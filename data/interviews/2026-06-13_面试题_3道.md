## Q1: 高并发场景下的Tool Calling限流与优雅降级

难度: Senior / Staff
领域: 生产化AI / Agent架构 / Tool Calling
场景: 在今日处理内部知识库问答Agent时，发现用户激增导致下游搜索服务（基于Elasticsearch）触发429 Too Many Requests。Agent原本设计的并行Tool Calling策略（一次Query调用3个不同的搜索工具）进一步放大了下游压力。

题目:
设计一套基于LangChain4j的Tool Calling治理方案，要求在不显著增加用户感知延迟（P99 < 2s）的前提下，解决并发过载问题。请详细阐述如何实现请求队列、超时控制以及失败重试策略，特别是当部分Tool（如搜索）失败而其他Tool（如数据库查询）成功时，Agent应如何生成Partial Answer（部分答案）。

答案要点:
1. 核心思路：引入令牌桶或RateLimiter对LLM Tool Execution进行节流，利用Java Virtual Threads实现非阻塞并发控制。
2. 具体方案（含代码）：
   ```java
   public class ResilientToolExecutor {
       private final RateLimiter rateLimiter;
       private final ExecutorService virtualThreadExecutor;
   
       @Tool("Search internal docs")
       public String searchDocs(String query) {
           // Acquire permit or fail fast based on priority
           if (!rateLimiter.tryAcquire(500, TimeUnit.MILLISECONDS)) {
               throw new ToolOverloadException("Search service busy");
           }
           return performSearch(query);
       }
   
       // Use structured output to guide LLM on partial failures
       @UserMessage("System: Tools might fail. Use available data.")
       public EnhancedResponse query(@V("userQuery") String query) { ... }
   }
   ```
3. 权衡分析：丢弃部分请求 vs 排队等待；重试可能带来的延迟放大 vs 数据新鲜度。
4. 反面教训：不要在LLM流式输出过程中进行阻塞的Tool调用，这会导致TTFT（Time to First Token）激增。
5. 衡量指标：Tool Success Rate, Token Usage per Partial Answer, P99 Latency.

面试官会关注什么:
- 候选人是否提到Virtual Threads来处理高并发IO等待。
- 常见误区：简单地让LLM重试所有Tool，导致请求风暴。
- 可追问：如何根据Tool的重要性定义优先级？如何向用户透明地展示“部分结果”？

## Q2: MCP协议下的多源异构数据安全访问控制

难度: Staff
领域: MCP协议 / 系统设计 / 安全模型
场景: 公司正在迁移到MCP (Model Context Protocol) 架构，统一的Host连接了多个不同的Servers（如Jira Server, GitHub Server, 私有文件Server）。今日Code Review中发现，某个Agent在处理用户请求时，试图通过MCP工具列表遍历的方式探测所有可用的Project ID，存在严重的数据泄露风险。

题目:
设计一套基于MCP的细粒度权限校验机制。假设你有User Context (LDAP groups) 和 Resource Context (Project Ownerships)。如何在LLM发起Tool调用之前，通过MCP Server端或中间件层拦截非法请求？请给出基于Capability Discovery的改进方案。

答案要点:
1. 核心思路：MCP Server不应暴露通用的CRUD接口，而应暴露经过User Context过滤后的Resource Lists（Dynamic Tool Discovery）。
2. 具体方案（含代码）：
   ```json
   // MCP Server Response (filtered)
   {
     "tools": [
       {
         "name": "get_issue",
         "inputSchema": {
           "type": "object",
           "properties": {
             "project_id": { 
               "type": "string", 
               "enum": ["PROJ_A", "PROJ_B"] // Pre-filtered allowed IDs
             }
           }
         }
       }
     ]
   }
   ```
   Java端校验逻辑：
   ```java
   public class McpSecurityGuard {
       public List<Tool> getAuthorizedTools(User user) {
           List<String> allowedProjects = authService.getUserProjects(user);
           return toolRegistry.findAll().stream()
               .map(tool -> tool.restrictSchema("project_id", allowedProjects))
               .toList();
       }
   }
   ```
3. 权衡分析：在MCP Server端过滤（网络延迟增加但安全性高） vs 在Host端过滤（实现复杂）。
4. 反面教训：仅依赖Prompt中的“不要访问未授权数据”是不够的，LLM会产生幻觉或越狱。
5. 衡量指标：Unauthorized Access Attempts (Blocked), Tool Discovery Latency.

面试官会关注什么:
- 候选人是否理解MCP的Resource/Tool/Prompt三个核心概念的区别。
- 常见误区：试图在LLM生成Tool Call参数之后才做校验，导致浪费Token且增加安全风险。
- 可追问：如果权限变更频繁，如何动态更新Tool Schema而不重启Agent？

## Q3: 复杂规划任务中的ReAct循环发散控制与CoT优化

难度: Senior
领域: Agent架构 / Prompt工程 / 失败模式分析
场景: 在部署物流调度Agent时，观察到约5%的请求陷入了无限循环。Agent在使用ReAct模式时，不断重复调用“get_truck_status”工具，尽管返回结果并未变化，但LLM始终认为需要再次确认以生成最终计划。这导致了巨大的Token浪费和任务超时。

题目:
请分析这种Loop（循环）产生的根本原因，并提供一个结合Reflection（反思）和CoT（Chain of Thought）限制的解决方案。要求设计一个Supervisor架构，能够检测Agent的无效动作并强制进入终止或总结状态。

答案要点:
1. 核心思路：引入State Machine限制最大步骤数，并在System Prompt中强制要求Observation Comparison（观察对比）。
2. 具体方案（含代码）：
   ```java
   public interface LogisticPlanner {
       @SystemMessage("""
       You are a planner. Max 5 steps.
       If tool output is identical to previous step, stop and conclude immediately.
       Format your thinking: <thought>...status changed?...</thought>
       """)
       String plan(String request);
   }
   
   // Supervisor implementation
   public class StepMonitor {
       private int stepCount = 0;
       private String lastObservationHash = "";
   
       public ToolExecutionResult execute(ToolSpec tool, Args args) {
           if (stepCount > 5) return ToolExecutionResult.forceStop("Max steps reached");
           Result res = tool.run(args);
           
           if (hash(res.content).equals(lastObservationHash)) {
               return ToolExecutionResult.error("No progress detected, halting.");
           }
           stepCount++;
           return res;
       }
   }
   ```
3. 权衡分析：硬性限制Step数量可能导致复杂任务失败，需要结合“Human Hand-off”机制。
4. 反面教训：单纯依赖LLM“自律”是无效的，必须在代码层设置Guardrails。
5. 衡量指标：Average Steps per Task, Loop Detection Rate, Task Completion Rate.

面试官会关注什么:
- 候选人是否提到“环境状态”的概念，即LLM需要感知到外部世界未发生变化。
- 常见误区：仅仅增加Max Steps限制，而不解决无效重试的根本逻辑问题。
- 可追问：如何利用历史成功的Task Trajectories做Few-shot Prompting来减少循环？
