## 🤖 Q1: 递归式 Web Search Tool 中的并发去重与成本控制

**难度:** Senior / Staff
**领域:** Agent 架构 / Tool Calling / 生产化 AI
**场景:** 今天在实现一个能够深度溯源的 Web Search Agent，需要避免在多次 ReAct 循环中重复访问同一个 URL，同时控制 Token 消耗。

**题目:**
在 ReAct 循环中，LLM 经常会决定搜索子链接来验证信息，这很容易导致无限循环（A->B->C->A）或者重复抓取相同的高权重页面。请设计一套 Tool Calling 机制，既能利用 LLM 的规划能力并发执行多步搜索，又能有效去重和剪枝。如果 LLM 执意要访问已访问过的 URL，如何在 System Prompt 和代码层面双重拦截？

**答案要点:**
1. **核心思路：** 构建“上下文感知的 Tool Middleware”，在 Tool 执行前通过 Ephemeral State（短暂状态）进行校验，而非完全依赖 LLM 记忆。
2. **具体方案：** 使用 `@Tool` 装饰器配合 Python 的 `functools.lru_cache` 或 Redis 存储已访问 URL 集合。设计一个 `parallel_search` 工具，内部由 Agent 并发调用，但在执行层做 `visited_urls` 检查。若 LLM 调用已访问 URL，直接返回 Cached Result 而非真实网络请求，或返回特定的 Hint 迫使其转向。
   ```python
   # Pseudo-code using LangChain4j/Python style logic
   visited_urls = set()

   @tool
   def scrape_url(url: str):
       if url in visited_urls:
           return f"Error: Content already fetched from {url} in current context. Do not retry."
       visited_urls.add(url)
       return actual_http_client.get(url)
   ```
3. **权衡分析：** 选择了“记忆注入”而非“Prompt 强约束”，因为 LLM 在长上下文中极易遗忘 Prompt 指令；放弃了完全禁止，而是允许 LLM 意识到“已访问”，保留了其自主性。
4. **反面教训：** 常见错误是在 Prompt 里写“不要重复搜索”，效果极差；另一种错误是只做简单的 URL 字符串去重，忽略了 query parameter 带来的差异（例如 `?page=1` vs `?page=2` 应视为不同，但 `?utm_source=twitter` 应视为相同）。
5. **指标衡量：** 搜索步数、重复请求率（目标 < 5%）、Token 消耗总量、最终答案的准确率。

**面试官会关注什么:**
- 候选人是否区分了“LLM 逻辑层的去重”和“执行层的去重”？
- 是否考虑了并发情况下的线程安全问题？
- 如何处理 LLM 产生幻觉 URL 的情况？

## 🤖 Q2: 供应链分析 Agent 中的结构化输出与数据校验

**难度:** Senior
**领域:** Prompt 工程 / 生产化 AI / LangChain4j
**场景:** 我们正在开发一个分析非结构化供应链 PDF 报告的 Agent，必须提取出“原材料名称、单价、供应商风险等级”等字段，且要求 100% 的 JSON 格式成功率。

**题目:**
在使用 GPT-4o 进行 Structured Output 提取时，偶尔会出现 JSON Schema 不匹配（例如 Risk Level 枚举值写成了 "High" 而不是规定的 "H"，或者 Date 格式混乱）。单纯依靠 System Prompt 往往无法达到 100% 的鲁棒性。请设计一个“自修复流水线”，当 Tool 接收到不合规的 JSON 时，如何在不增加过多 Latency 的前提下进行自动修正？如果 LLM 连续两次修正失败，降级策略是什么？

**答案要点:**
1. **核心思路：** 采用“LLM-as-Judge”或 Pydantic/JSON Schema 强校验，构建一个闭环的“生成-校验-重试”机制。
2. **具体方案：** 定义严格的 JsonSchema 类。在 Tool 或 Service 层捕获 `ValidationException`。如果失败，将原始错误信息和新的一轮修正 Prompt（包含具体的 Error Message）喂回给 LLM 进行局部修正，而不是重新生成整个大文档。
   ```java
   // LangChain4j Style Service
   public interface SupplyChainExtractor {
       @UserMessage("Extract data from {{text}}. Strictly follow the JSON schema.")
       @StructuredOutput(ReportData.class) // Enforces schema during generation
       ReportData extract(String text);
   }
   
   // Fallback logic in code
   try {
       return extractor.extract(pdfText);
   } (ValidationException e) {
       return retryWithFocusedPrompt(pdfText, e.getMessage());
   }
   ```
3. **权衡分析：** 选择了结构化输出 API（如 OpenAI 的 JSON Mode）而非纯 Prompt，这能显著减少 Parsing 错误；放弃了极其复杂的正则后处理，因为业务逻辑字段（如 Risk）需要语义理解。
4. **反面教训：** 最危险的错误是“静默失败”，即把错误的 JSON 默认值填入导致数据污染。必须确保校验失败时阻断流程或标记为“人工审核”。
5. **指标衡量：** JSON 解析成功率（目标 99.9%）、单次提取延迟（P99 < 3s）、人工介入率。

**面试官会关注什么:**
- 候选人是否了解 JSON Mode / Structured Output 的底层限制？
- 如何设计 Prompt 让 LLM 在第二次尝试时只修正错误字段，而不是改乱正确的部分？
- 成本与延迟的平衡点在哪里？

## 🤖 Q3: ReAct 循环中的“记忆污染”与长上下文管理

**难度:** Staff
**领域:** Agent 架构 / 生产化 AI / 失败模式分析
**场景:** 今天遇到一个严重的 Agent 失败案例：在一个需要 15 步推理的复杂数据库查询任务中，Agent 在第 10 步产生了一个 SQL 语法错误，随后的 5 步尝试修复时，不断被自己之前的错误 SQL 结果干扰，导致最终陷入死循环。

**题目:**
在 ReAct 模式下，如果 Agent 陷入“尝试-失败-再尝试”的死循环，且 Context Window 快要耗尽，如何设计一个“记忆截断与清洗”机制？请给出具体的算法或策略来决定哪些历史 Observation 应该被丢弃，哪些 Error Trace 必须保留？同时，如何判断 Agent 是在“解决问题”而不是在“空转”？

**答案要点:**
1. **核心思路：** 引入“反思与总结”机制，定期将长对话历史压缩为“高层摘要”，并识别并标记“失败的路径”作为负面约束。
2. **具体方案：** 设定一个 sliding window（例如保留最近 5 轮对话），但同时维护一个 `global_summary` 和 `negative_constraints` 列表。如果检测到同样的 Error 出现 2 次以上，触发 `Evaluator` 分支，强制 Agent 生成“假设错误原因”的摘要，并将此摘要注入 System Prompt，替换掉具体的冗长历史记录。
   ```python
   # Conceptual logic
   def update_memory(history, last_observation):
       if is_error(last_observation):
           error_count = count_consecutive_errors(history)
           if error_count > 2:
               # Trigger Summarization
               summary = llm.summarize_errors(history)
               history.clear()
               history.append(SystemMessage(f"Previous attempts failed due to: {summary}. Avoid these paths."))
   ```
3. **权衡分析：** 选择了动态摘要而非固定窗口，因为早期的成功推理对后期可能依然重要；放弃了完全重置 Context，因为这会让 Agent 忘记用户的初始意图。
4. **反面教训：** 常见错误是直接丢弃最早的 Token，导致 Agent 忘记了 Goal；另一种错误是没有显式告知 Agent“你刚才失败了”，导致它再次尝试同样的错误。
5. **指标衡量：** 任务完成率、平均步数、Token 消耗量、死循环检测准确率。

**面试官会关注什么:**
- 候选人是否提到“滚动摘要”技术？
- 如何量化“空转”？（例如 Semantic Similarity 连续几次都很高）
- 在极端情况下，如何设计“熔断”机制直接转人工？

## 🤖 Q4: MCP 协议下的多源数据异构查询与超时处理

**难度:** Senior / Staff
**领域:** MCP 协议 / Tool Calling / 系统设计
**场景:** 我们正在整合三个不同的 MCP Server（一个是本地 Postgres，一个是远程 Snowflake，一个是第三方 CRM API）。CRM API 响应极不稳定（偶发 30s 超时），导致整个 Agent 工作流经常卡死。

**题目:**
基于 MCP 协议，如果 Supervisor Agent 需要并行调用这三个数据源，而其中一个 Tool 超时或报错，如何设计架构保证 Agent 能基于“部分结果”继续给出建议，而不是直接抛出异常终止？请描述你在 Tool Specification 层面和 Runtime 层面的具体设计，并解释如何向 LLM 表达“数据缺失”的语义。

**答案要点:**
1. **核心思路：** 实现严格的“超时熔断”与“降级响应”机制，将底层网络异常转化为 LLM 可理解的业务语义提示。
2. **具体方案：** 在 MCP Client 层配置超时参数（如 5s），并使用 `Any` 类型捕获所有异常。不要直接返回 Stack Trace，而是返回一个特定的 Tool Result 对象，描述状态和数据的不完整性。例如，CRM 查询失败时返回 `{"status": "timeout", "partial_data": null, "message": "CRM data unavailable, proceed with internal DB only."}`。
3. **权衡分析：** 选择了“Fast Fail”策略，放弃了耗时过长的重试，因为在 Agent 交互场景下，用户的耐心阈值通常很低；选择了向 LLM 汇报“数据源不可用”而不是默默忽略，因为 LLM 需要根据数据来源调整结论的置信度。
4. **反面教训：** 致命错误是将 Python Exception 直接喂给 LLM，这不仅浪费 Token，还容易让 LLM 产生混淆或尝试去解析错误代码。另一个错误是同步等待所有 Tool 返回，导致“长尾效应”拖垮整体延迟。
5. **指标衡量：** P95 延迟（受慢速 Tool 影响程度）、部分成功率、失败场景下的答案质量。

**面试官会关注什么:**
- 候选人是否熟悉 MCP 协议中的 Resource 和 Tool 的区别？
- 如何在 Prompt 中指导 LLM 处理 `null` 或 `missing` 的数据？
- 是否考虑过幂等性设计？
