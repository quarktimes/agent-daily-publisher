## Q1: LLM 输出的“软硬兼施”防御机制设计

**难度：** Senior / Staff
**领域：** 生产化AI / Prompt工程 / 边界情况处理
**对应工作：** 编写 `format_sanitizer.py` 解决 LLM 生成的 Markdown 代码块渲染失败问题（渲染率从 60% 提升至 100%）。

**题目：**
LLM 在生成技术文档时，Prompt 中已经明确要求输出标准 Markdown 代码块，但实际运行中仍有约 40% 的概率出现代码块符号缺失、语言标识符错误或嵌套混乱，导致下游渲染引擎崩溃。你既不能无限增加 Token 成本去写超长 Prompt，又必须保证输出 100% 可用。请设计一套防御机制，结合 Prompt（软约束）和后处理代码（硬约束），确保代码块结构的完整性。如果 LLM 返回了 ```java ```python ``` 这种嵌套错误，你的正则或解析逻辑如何处理？

**答案要点：**
1. **核心思路**：Prompt 负责语义正确性（软约束），正则/AST 解析器负责语法结构完整性（硬约束）。建立“清洗-验证-修复”三层管道。
2. **技术方案**：
```python
import re

def sanitize_markdown_code_blocks(text: str) -> str:
    """
    Post-process LLM output to ensure strict Markdown code block format.
    Strategy: Detect malformed blocks and enforce strict ```lang\n ... \n``` structure.
    """
    # 1. Fix common backtick issues (e.g., single backtick for code)
    # Replace single backtick phrases that look like code with triple backticks if not properly closed
    # This is a heuristic; strict parsing requires a state machine.
    
    # 2. Validate and repair code blocks using a state machine approach
    lines = text.split('\n')
    output_lines = []
    in_code_block = False
    current_lang = ''
    
    for line in lines:
        stripped = line.strip()
        
        # Detect start of a code block
        if stripped.startswith('```'):
            if not in_code_block:
                # Start block: Extract language
                in_code_block = True
                # Normalize start tag: ensure it is just ```lang
                lang_part = stripped[3:].strip()
                # Default to 'text' if no lang specified
                current_lang = lang_part if lang_part else 'text'
                output_lines.append(f'```{current_lang}')
            else:
                # End block
                in_code_block = False
                output_lines.append('```')
        else:
            # Content line
            if in_code_block:
                # Check for accidental nested triple backticks inside the block (common LLM error)
                if '```' in line:
                    # Escape or remove internal backticks to prevent early termination
                    line = line.replace('```', '\`\`\`')
            output_lines.append(line)
    
    # 3. Handle unclosed blocks (deterministic recovery)
    if in_code_block:
        output_lines.append('```')
        print("[Sanitizer Warning] Unclosed code block detected. Force-closed.")
        
    return '\n'.join(output_lines)
```
3. **权衡分析**：
   *   选正则/状态机：速度快，延迟低，逻辑确定。缺点是可能误伤合法内容（如文本中讨论 backtick 字符）。
   *   选 LLM 修复：语义理解好，但成本高、延迟大、且不可靠（可能修了A坏了B）。
   *   结论：工程上首选代码硬约束，仅在无法通过规则修复时（如语义严重错误）才考虑 LLM 重试。
4. **反面教训**：
   *   曾尝试只依赖 System Prompt 中的“Strict JSON/Markdown Mode”指令，结果在高并发下失效，因为概率性问题无法通过提示词彻底消除。
   *   错误做法：简单的 `replace('\`\`\`', '')` 会把正确的代码块分隔符也删掉，导致整个文档合并成一个代码块。
5. **量化指标**：
   *   引入该管道后，文档渲染失败率从 40% 降至 <0.1%。
   *   Post-processing 延迟增加 <5ms，相比 LLM 生成时间可忽略不计。

**面试官视角：**
*   **加分项（+20）**：提到使用状态机而非简单正则，特别是处理“嵌套代码块”或“未闭合代码块”的逻辑；提到 LLM 的输出是概率分布，必须接受后处理是标准工程实践。
*   **扣分项（-20）**：回答“优化 Prompt 就能解决”，或者“扔给 LLM 再修一次”。这显示缺乏生产环境兜底思维。
*   **常见错误回答**：“用 markdown 库解析”。如果源文本本身不合法（如缺少闭合符号），大部分标准库会直接抛异常或吞掉内容，无法做到“修复并继续”。
*   **可以追问**：如果 LLM 在代码块里输出了“这是代码示例：```python...”，你的逻辑会不会误判？怎么解决？（考察边界 case 处理）

## Q2: 双轨制跨平台渲染架构设计

**难度：** Senior
**领域：** Agent架构 / 系统设计 / 模板引擎
**对应工作：** 决策采用“公众号 Markdown Nice + 通用平台 Jinja2”的双轨制架构，而非单一 Agent 或单一模板方案。

**题目：**
你需要设计一个 Agent 内容分发系统，支持将同一篇 LLM 生成的技术文档同时发布到微信公众号、Dev.to 和个人博客。微信公众号要求复杂的 CSS 样式（居中、色彩、特殊字体），而 Dev.to 要求纯净的 GitHub Flavored Markdown。团队中有人提议让 LLM 充当“排版 Agent”，针对不同平台生成不同版本的 HTML。请评估这个方案，并画出你主张的架构图。重点解释：为什么不把排版逻辑交给 Agent？当平台扩展到 10 个时，你的系统如何避免维护灾难？

**答案要点：**
1. **核心思路**：分离“内容生成”与“表现形式”。LLM 负责生成结构化的语义数据（如 JSON/Markdown），模板引擎负责特定平台的视觉渲染。
2. **技术方案**：
   *   **架构组件**：
       1.  **Content Agent**: 产生 Standard Markdown (无样式)
       2.  **Format Adapter (Router)**: 根据 Target Platform 选择渲染策略
       3.  **Jinja2 Engine**: 处理通用平台
       4.  **Markdown Nice Wrapper**: 处理公众号
```python
# Pseudo-code for the Rendering Pipeline
from jinja2 import Template

class PublishingOrchestrator:
    def publish(self, content: str, platform: str):
        # 1. Content is platform-agnostic Markdown
        markdown_content = content 
        
        if platform == 'wechat':
            # Track A: Specialized tooling for high-maintenance platforms
            html = self._render_with_markdown_nice(markdown_content)
        else:
            # Track B: Standardized template for scalable platforms
            html = self._render_with_jinja2(markdown_content, platform)
            
        self._api_call(platform, html)

    def _render_with_jinja2(self, md: str, platform: str) -> str:
        # Template injection logic
        template = self.jinja_env.get_template(f"{platform}.html")
        # Could use a markdown-to-html filter here
        return template.render(content=md, date="2026-06-14")

    def _render_with_markdown_nice(self, md: str) -> str:
        # Call external API or CLI tool for WeChat formatting
        return markdown_nice_client.convert(md, theme="modern")
```
3. **权衡分析**：
   *   **选模板引擎**：快、稳定、可版本控制。修改样式只需改模板文件，无需改 Prompt 或重跑 LLM。
   *   **弃排版 Agent**：LLM 生成 HTML 极易产生幻觉（如未闭合标签），且调整样式需要反复调试 Prompt，成本极高。对于确定性的排版需求，代码优于模型。
4. **反面教训**：
   *   早期尝试让 Agent 直接写 HTML，结果一旦需求改“字体变大一点”，就需要重新设计 Prompt 并重新生成整篇文章，浪费成本且无法精确控制像素级样式。
   *   “一切皆 Agent”的陷阱：不要把确定性任务外包给概率模型。
5. **量化指标**：
   *   样式调整迭代时间从“小时级（Prompt调试）”降至“分钟级（修改 Jinja2 模板）”。
   *   渲染成本：模板引擎几乎为 0，相比每次调用 LLM 生成 HTML 节省 100% 成本。

**面试官视角：**
*   **加分项（+20）**：明确提出“单一数据源，多态视图”的设计模式；提到使用“Markdown AST”作为中间格式来处理复杂转换。
*   **扣分项（-20）**：坚持要用 Agent 生成 HTML，认为“Agent 更智能”；或者没有意识到微信公众号的特殊性，试图用一套标准 Markdown 搞定所有平台（这在实际工作中会被产品经理打回）。
*   **常见错误回答**：“为每个平台写一个独立的 Agent”。这会导致 N 个平台就有 N 套逻辑，维护成本线性爆炸。
*   **可以追问**：如果 Markdown Nice 的 API 挂了，或者 Dev.to 更新了它的 Markdown 解析器，你的架构怎么容错？（考察降级策略和隔离性）

## Q3: 提示词工程中的“评分锚点”落地

**难度：** Senior
**领域：** Prompt工程 / Agent效果评估
**对应工作：** 优化 Agent 提示词，引入 CoT（思维链）、示例对比和自检清单，将标题吸引力和结构质量显著提升。

**题目：**
你负责优化一个“标题生成 Agent”。之前的 Prompt 是“请生成一个吸引人的标题”，结果输出方差极大，有时像新闻标题，有时像论文标题，且不可控。现在的需求是让生成的标题必须符合“高点击率”且“技术准确”。你会如何在 System Prompt 中引入“评分锚点”和“自检清单”来收敛 LLM 的输出？请给出优化前后的 Prompt 对比，并解释为什么加了这几句效果会变好？

**答案要点：**
1. **核心思路**：将模糊的定性需求（“吸引人”）转化为可执行的定量步骤（“通过检查清单”）。利用 LLM 的模仿能力，通过 Few-Shot 示例锁定风格。
2. **技术方案**：
   *   **优化前**：
       ```text
       Role: Tech Writer.
       Task: Write a title for the blog post below.
       Requirement: Make it attractive.
       ```
   *   **优化后**：
       ```text
       Role: Senior Tech Editor at a top-tier dev community.
       Task: Write a title for the blog post below.
       
       Constraints:
       1. Length: 10-25 Chinese characters.
       2. Structure: [Benefit] + [Technical Keyword].
       
       Scoring Anchors (Quality Standard):
       - Score 5 (Perfect): Provokes curiosity, contains a specific tech stack (e.g., Rust, K8s), implies a clear benefit.
       - Score 3 (Average): Generic tech keyword, standard sentence structure.
       - Score 1 (Fail): Vague, clickbait without substance, or too academic.
       
       Self-Check List (CoT):
       Before outputting, verify:
       - [] Does it contain the core technology mentioned?
       - [] Is the tone professional yet catchy?
       - [] Does it avoid exaggeration?
       
       Few-Shot Examples:
       Input: A guide to using Python async.
       Output: 深入 Python 异步编程：提升 I/O 密集型应用性能的关键
       ```
3. **权衡分析**：
   *   **选详细锚点**：Prompt 变长，Token 成本增加，但输出质量稳定性大幅提升，减少下游人工审核成本。
   *   **选简单 Prompt**：Token 省了，但需要大量人工筛选或二次生成，综合成本更高。
4. **反面教训**：
   *   只给“要吸引人”这种形容词，LLM 会基于训练集中权重最高的“营销号”风格生成，导致技术文档标题变得像震惊体。
   *   缺少 Self-Check List 时，LLM 容易忽略长度限制或关键词要求。
5. **量化指标**：
   *   标题可用率（人工直接采纳比例）从 30% 提升至 85%。
   *   标题长度超限率从 20% 降至 0%。

**面试官视角：**
*   **加分项（+20）**：提到“Scoring Anchors”不仅是给 LLM 看，也是为了后续建立自动评估指标；提到 CoT 能够强制 LLM 在输出前进行推理，从而减少幻觉。
*   **扣分项（-20）**：只会写“请你仔细思考”这种无效指令；给出的 Prompt 依然没有量化标准（如长度、关键词）。
*   **常见错误回答**：“我会微调一个模型”。对于仅优化 Prompt 能解决的问题，微调是大材小用且迭代慢，不符合工程效率。
*   **可以追问**：如果 LLM 生成的标题虽然符合所有 Check List，但依然很烂（虽然符合长度但读起来不通顺），你会怎么进一步优化？（考察对 LLM 局限性的理解和人机协同策略）
