## 🔧 问题和方案

### 🔒 AI 生成内容导致敏感数据泄露风险
**背景**：当基于代码库生成技术文章并发布到 Dev.to 或 CSDN 等公共平台，或上传源码至 GitHub 时，AI 很可能将配置文件中的 API Key、数据库连接串或 Redis 配置作为“示例代码”写入文章中。

**根因分析**：LLM 在进行 RAG（检索增强生成）时，缺乏对上下文中敏感信息的自动识别能力。它只是将代码片段视为文本进行重组，无法区分 `DATABASE_URL` 和普通字符串的区别。单一的防御手段（仅在发布前检查）很容易被绕过。

**方案**：实施了**三层纵深防御体系**：

1.  **Pre-commit Hook 层**：利用 Git 钩子在提交前扫描暂存区，拦截包含 `jdbc:`, `redis://`, `api_key` 等特征词的文件。
2.  **Runtime Pipeline 层**：在发布管道中增加过滤器，对即将生成的 Markdown 内容进行正则匹配清洗。
3.  **Prompt 层**：在 System Prompt 中注入强隐私指令，明确告知 AI “不要包含真实凭证，请使用占位符如 `YOUR_API_KEY`”。

**效果**：彻底杜绝了因自动发布导致的凭证泄露风险，使得 AI 自动化博客流程可以安全地在公开仓库运行。

### 🐉 微信公众号 API 发布全链路故障
**背景**：在尝试通过微信官方 API 自动发布草稿时，遇到了一连串报错，包括媒体上传失败、标题超限以及乱码问题，导致自动化流程中断。

**根因分析**：微信 API 的限制比文档描述更为隐蔽且严格：
1.  **媒体类型混淆**：上传封面图时，必须指定 `type=thumb` 而非通用的 `image`，否则后续接口无法调用。
2.  **标题长度陷阱**：微信限制的是 **64 字节** 而非 64 个字符。一个中文字符占 3 字节（UTF-8），这意味着中文标题实际上只能容纳约 21 个汉字。直接用 `len()` 判断会导致错误。
3.  **编码问题**：接口对 JSON 字符串的 UTF-8 编码格式极其敏感，未显式声明编码可能导致特殊字符报错。

**方案**：在 `wechat_api.py` 中实现了鲁棒性更强的处理逻辑：

```python
import re

def sanitize_wechat_title(title: str) -> str:
    # 微信限制 64 字节，为了安全截断到 60 字节
    # encode('utf-8') 将字符转换为字节，计算真实占用空间
    byte_length = len(title.encode('utf-8'))
    if byte_length <= 60:
        return title
    
    # 简单的截断逻辑：按字符回溯，确保不超过限制
    truncated = []
    current_len = 0
    for char in title:
        char_len = len(char.encode('utf-8'))
        if current_len + char_len > 60:
            break
        truncated.append(char)
        current_len += char_len
    
    return "".join(truncated) + "..."

# 上传封面时明确指定 thumb 类型

```

**效果**：API 发布成功率从 0% 提升至 100%，解决了自动化发布最后的一公里问题。

### 🌐 微信 API IP 白名单限制导致的部署困境
**背景**：微信官方 API 要求调用服务器的 IP 必须在后台配置的白名单内。然而，现代 CI/CD 环境（如 GitHub Actions）或家庭宽带环境通常使用动态 IP，频繁手动更新白名单是不现实的。

**根因分析**：这是微信的安全模型与云原生/动态基础设施之间的冲突。API 依赖静态 IP 做信任基础，而自动化发布任务往往运行在 ephemeral（临时性）环境中。

**方案**：采用了**API + 浏览器自动化混合策略**。优先使用 Playwright 进行浏览器模拟发布，绕过 IP 限制；仅在浏览器自动化失败或不可用时降级使用 API（此情况通常发生在有固定 IP 的 VPS 上）。

**效果**：消除了对网络环境的强依赖，使得无论在本地运行还是云端 CI 中，发布流程都能稳定工作。

## 🏗 架构决策

### 1. 混合发布架构（REST API vs Browser Automation）

**决策内容**：针对不同平台采取差异化的发布策略。Dev.to 使用标准 REST API；CSDN 使用 Playwright 浏览器自动化（因其无开放 API）；微信公众号采用浏览器优先、API 兜底的策略。

**备选方案**：
- 全员 API：不可行，CSDN 等平台不提供。
- 全员浏览器：可行，但极其不稳定，页面 DOM 变动会导致全盘失效。

**选择理由**：在稳定性和覆盖率之间寻找平衡。API 虽好但并非处处皆有，浏览器自动化虽然脆弱但能覆盖“无 API”场景。针对微信这种“有限制 API”的情况，双路切换能最大化可用性。

### 2. 基于环境变量的凭证管理

**决策内容**：所有敏感凭证（如 App ID, App Secret）严禁写入代码，必须通过 `os.environ` 读取，并在 `.zshrc` 或 CI Secrets 中配置。

**备选方案**：
- 配置文件（如 `config.json`）：容易误提交。
- 加密配置库：过度设计，增加维护成本。

**选择理由**：这是业界标准实践。配合 `.gitignore` 和前文提到的 Pre-commit Hook，能以最低的成本实现最高的安全性。任何开发者克隆代码后，只需设置自己的环境变量即可运行。

## 💡 关键收获

1.  **字节与字符的坑**：在处理中文内容的 API 限制时，永远不要假设“长度限制”等于“字符数限制”。微信、短信服务等通常基于字节计算，UTF-8 编码下中文字符占 3 字节，这一点在做截断逻辑时必须显式处理。

2.  **防御深度的必要性**：对于 AI 生成的公开内容，单点防御是靠不住的。Prompt 层只能“建议”，Runtime 层可以“拦截”，而 Pre-commit 层则是“最后的防线”。只有三层协同，才能真正消除数据泄露的焦虑。

3.  **外部 API 的容错设计**：在设计依赖第三方平台的系统时，不仅要考虑接口怎么调，还要考虑接口“调不通”或“有苛刻准入条件”时怎么办。浏览器自动化虽然看起来笨重，但在面对 IP 白名单这种硬性壁垒时，反而是最灵活的破局方案。
