## 🔧 问题和方案

### 微信公众号发布的双模执行方案

**背景**
在构建多平台发布系统时，微信公众号的接入是一个典型的工程难点。官方提供了素材管理 API，允许通过程序上传和发布草稿，但这要求服务器的 IP 地址必须在微信公众平台的后台白名单中。对于在本地开发、云端部署或动态 IP 环境下运行的自动化 Agent 来说，这增加了极大的运维成本和部署摩擦。

**根因分析**
单一依赖官方 API 会导致系统环境耦合度太高。如果目标平台设置了严格的网络准入策略（如 IP 白名单），不仅部署流程会被打断，而且在混合云或多 IP 负载均衡场景下难以维护。我们需要一种不依赖平台特定网络配置的通用接入方式。

**方案**
我们设计并实现了一个双模执行器。优先调用官方 Draft API，因为它速度快、稳定性高；当检测到 IP 未授权或 API 调用失败时，自动降级为浏览器自动化模式。

```python
# 伪代码示例：双模发布策略
def publish_wechat(article):
    try:
        # 尝试使用官方 API
        if is_ip_whitelisted():
            return publish_via_api(article)
    except APIError as e:
        logger.warning(f"API publish failed: {e}, falling back to browser automation")
    
    # 降级到浏览器自动化
    return publish_via_selenium(article)
```

浏览器自动化通过模拟用户登录后台操作，绕过了 IP 白名单限制，实现了“在哪里运行就能在哪里发布”的能力。

**效果**
该方案消除了微信公众号发布的部署门槛。开发人员在本地环境即可测试发布流程，无需频繁申请 IP 白名单变更，大大提升了 CI/CD 流水线的灵活性。

### AI 系统的三层隐私防护体系

**背景**
当我们让 AI 生成配置文件、脚本甚至 Git Commit 信息时，存在一个隐蔽但致命的安全隐患：AI 可能会无意间将训练数据中的 API Key、数据库密码或内部 URL “记忆”并输出到生成的代码或文本中。如果这些内容被提交到 Git 仓库，后果不堪设想。

**根因分析**
传统的安全手段通常集中在“静态配置”层面，如 `.env` 文件不提交。但在 AI Agent 场景下，敏感信息可能动态生成于 Prompt 的输出中。仅靠开发者肉眼审查或 `.gitignore` 是无法防范这种“动态泄露”的。

**方案**
实施了纵深防御的三层防护机制：

1.  **Pre-commit Hook（开发层）**：在 Git 提交前，利用 Husky 或自定义脚本扫描暂存区文件，匹配常见的密钥特征（如 `sk-...`, `password=`），拦截包含敏感信息的提交。
2.  **环境变量过滤（配置层）**：在系统加载配置时，自动清洗环境变量，防止敏感配置被意外注入到日志或非加密上下文中。
3.  **运行时扫描（执行层）**：在 AI 生成内容后、实际执行/写入文件前，通过正则或安全库（如 `detect-secrets`）扫描输出流。

**效果**
构建了一个针对 AI 生成内容的安全沙箱。即便 LLM 幻觉生成了虚假或真实的密钥，系统也能在代码落地前将其拦截并脱敏，确保 Repo 的清洁度。

### 生产环境 H5 分享链接 404 故障排查

**背景**
线上监控发现 `shop.tkstock.com` 域名下的 H5 分享链接大规模返回 404 Not Found，直接影响了营销页面的流量分发。

**根因分析**
排查后端应用日志发现，请求根本没有到达 Python/Node.js 服务层。通过检查 Nginx 的 `error.log` 和 `access.log`，确认问题出在反向代理配置上。Nginx 缺少针对 `/share/*` 路径的 `location` 块配置，导致无法将请求正确转发给后端服务处理。

**方案**
修改 Nginx 配置文件，补充缺失的路由规则，并重启服务。

```nginx
server {
    listen 80;
    server_name shop.tkstock.com;

    location /share/ {
        proxy_pass http://backend_upstream;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 其他配置...
}
```

**效果**
配置热加载后，H5 分享链接立即恢复正常访问，故障彻底解决。这也提醒我们，在排查特定路由的 404 问题时，应优先检查边缘网关（如 Nginx/Ingress）的配置映射。

## 🏗 架构决策

### 决策一：双模发布架构

**决定内容**
确立了“API 优先，浏览器自动化兜底”的发布器设计标准。

**考量过的替代方案**
- **纯浏览器自动化**：优点是通用性强，不需要申请 API 权限；缺点是速度慢，且 DOM 结构变化极易导致脚本维护困难。
- **纯 API 调用**：优点是性能最佳；缺点是部分平台（如微信公众号）有 IP 限制，部分平台根本不提供 API。

**胜出理由**
双模架构在可靠性和覆盖面之间取得了最佳平衡。对于 Dev.to 这类开放平台，使用 API 可以实现毫秒级发布；对于微信这类封闭平台，利用浏览器自动化保证了系统的可移植性。这种设计使得 Agent 系统在面对不同平台策略时具有极高的生存能力。

### 决策二：引入三层隐私防护

**决定内容**
在系统中强制实施 Pre-commit、环境过滤、运行时扫描的三层安全机制。

**考量过的替代方案**
- **仅依赖人工审查**：成本高且不可靠，无法应对 AI 批量生成的场景。
- **仅运行时扫描**：可以防止执行泄露，但如果开发者手动 `git commit` 仍可能绕过。

**胜出理由**
安全领域讲究“纵深防御”。单一防线极易被突破，三层防护覆盖了代码生成的全生命周期。虽然增加了一些计算开销和误报率，但对于处理敏感凭证的 AI 系统来说，这种鲁棒性是必须的。

## 💡 关键收获

1.  **浏览器自动化作为 API 的战略储备**：在设计自动化系统时，不要把浏览器自动化仅仅看作测试工具，它是突破平台 API 限制（如 IP 白名单、 Rate Limit）的有效战略储备。虽然它慢且脆弱，但它是解决“最后一公里”连通性的万能胶水。

2.  **AI 时代的安全新范式**：传统安全关注“不要把钥匙放在门口”，而 AI 安全需要关注“AI 可能会自己生成钥匙并放在门口”。运行时动态扫描 AI 输出内容是现代 LLM 应用不可或缺的一环。

3.  **Nginx 排查的黄金法则**：遇到特定路径 404，先看 Nginx。很多后端开发人员在 debug 时往往直奔代码逻辑，却忽略了流量根本没有进入应用的事实。检查网关层的路由映射规则应该是排查 404 的第一步。

4.  **防御深度的必要性**：单一的安全手段在复杂的 Agent 系统中形同虚设。Pre-commit hook 防住人为失误，运行时扫描防住 AI 幻觉，多层互补才能构建真正安全的自动化流水线。
