## 🔧 问题和方案

### 1. CSDN Open API 失效与浏览器自动化替代

**背景**：CSDN在2026年初悄然关闭了其公开的Open API接口，导致原有的基于HTTP请求的发布机制直接失效。团队需要快速找到替代方案，否则将丢失中国最大开发者社区之一的稿件分发渠道。

**根因分析**：CSDN官方并未发布任何API变更公告，但在一次常规维护后，所有API端点返回404和403，确认是服务端主动弃用。推测是CSDN出于安全或商业化考量，转向了不对外提供API的模式。

**方案**：采用Playwright驱动的浏览器自动化方案，模拟真实用户登录和文章发布流程。核心思路是：
- 使用Playwright启动一个无头Chromium浏览器
- 导航到CSDN的登录页面
- 通过二维码扫码完成一次手动登录
- 将登录后Cookies序列化到本地文件（`csdn_cookies.json`）
- 后续运行直接加载Cookies，跳过登录步骤
- 进入创作中心，通过CSS选择器定位编辑器，注入Markdown内容，填写标题，点击发布

核心代码片段（简略）：

```python
import asyncio
from playwright.async_api import async_playwright

async def publish_to_csdn(title: str, content_md: str):
    async with async_playwright() as p:
        browser = await p.chromium.launch(headless=True)
        context = await browser.new_context(storage_state="csdn_cookies.json" if exists else None)
        page = await context.new_page()
        await page.goto("https://mp.csdn.net/mp_blog/creation/editor")
        # 注入内容
        await page.evaluate(f'''() => {{
            const editor = document.querySelector('.editor-content');
            if (editor) {{
                editor.innerHTML = `{escaped_content}`;
                editor.dispatchEvent(new Event('input', {{ bubbles: true }}));
            }}
        }}''')
        # 填写标题
        await page.fill('#title-input', title)
        await page.click('button:has-text("发布")')
        await page.wait_for_url("**/mp_blog/manage/article*")
        if not exists:
            await context.storage_state(path="csdn_cookies.json")
        await browser.close()
```

**效果**：成功实现了一次性发布。首次需要手动扫码，后续运行完全自动化。虽然比API调用慢3-5秒，但解决了“无API可用”的难题。

### 2. Playwright 动态编辑器选择器调试

**背景**：CSDN的Markdown编辑器并非标准的`<textarea>`或单纯的`contenteditable`，而是一个多层嵌套的富文本组件，包含shadow DOM和动态生成的元素。初始时，简单的`page.fill()`和`page.type()`都无法将内容注入正确位置。

**根因分析**：编辑器内部使用了`contenteditable`属性，但其外层的容器结构复杂，且编辑器内容可能被Vue或React的状态管理包裹。常规的`fill()`方法会尝试直接输入，但编辑器可能因事件监听缺失而不更新内部状态。

**方案**：经过多次迭代，最终采用以下组合：
- 使用`page.evaluate()`直接设置`innerHTML`，并手动触发`input`事件以通知框架更新。
- 标题输入框虽是一个明显的`<input>`元素，但页面动态渲染后需要确保已获取焦点，因此先`.focus()`再使用`page.keyboard.type()`模拟逐字输入。
- 发布按钮的点击在DOM加载完毕后增加显式等待。

```python
# 标题输入修复
await page.click('#title-input')
await page.wait_for_timeout(300)
await page.keyboard.type(title, delay=50)
```

**效果**：内容注入和标题输入的行为稳定，连续测试10次均未出现空白编辑器或标题丢失的情况。

### 3. Claude Code 历史日志格式变更

**背景**：在集成会话捕获钩子时，发现升级到Claude Code 2.1.143版本后，`history.jsonl`文件不再像往常一样出现。怀疑是数据丢失。

**根因分析**：Claude Code在2.1.143版本中改变了会话日志的存储结构：从单一的全局`~/.claude/history.jsonl`变更为每个项目独立的`~/.claude/projects/<project-name>/logs/`目录。原有的钩子只扫描全局路径，因此找不到数据。

**方案**：更新会话捕获钩子，先检查新路径，若不存在则回溯旧路径。同时增加版本检测，若Claude Code版本 >= 2.1.143 则直接使用新路径。

```python
import pathlib
import subprocess

def get_history_path():
    version = subprocess.run(["claude", "--version"], capture_output=True, text=True).stdout
    if parse_version(version) >= (2, 1, 143):
        return pathlib.Path.home() / ".claude" / "projects" / get_current_project() / "logs"
    else:
        return pathlib.Path.home() / ".claude" / "history.jsonl"
```

**效果**：会话数据捕获恢复正常，未丢失任何历史记录。

## 🏗 架构决策

### 决策1：选用 Playwright 而非 Selenium

**决定**：使用Playwright作为浏览器自动化框架。

**备选方案**：Selenium WebDriver + ChromeDriver。

**原因**：
- Playwright提供原生异步支持（`asyncio`），与项目现有的异步管线完美结合。
- 内置的自动等待机制大幅减少`time.sleep()`的滥用，提高稳定性。
- 选择器引擎更强大，支持`contenteditable`元素的直接定位（虽然最终用了evaluate）。
- 社区报告显示Playwright在处理SPA（单页应用）中的动态DOM时比Selenium更可靠。

**权衡**：Playwright的依赖包更大（约100MB额外），团队中部分成员更熟悉Selenium。但鉴于CSDN编辑器的复杂性，稳定性优先。

### 决策2：平台配置统一为 YAML 文件

**决定**：所有平台相关的设置（发布类路径、Cookies文件位置、选择器、API端点）集中存储在`platforms.yaml`中。

**备选方案**：将配置硬编码在Python模块中，或使用环境变量。

**原因**：
- 新增平台时无需修改发布器核心代码，只需增加一个YAML节点并实现对应的Publisher类。
- 支持在不同环境下（开发、测试、生产）通过不同的`platforms.yaml`切换凭证。
- 方便进行试运行（dry-run），通过配置控制是否实际发布。

```yaml
platforms:
  csdn:
    publisher_class: publishers.csdn.CSDNPublisher
    login_url: "https://passport.csdn.net/login"
    editor_url: "https://mp.csdn.net/mp_blog/creation/editor"
    cookie_file: "csdn_cookies.json"
  wechat_mp:
    publisher_class: publishers.wechat_mp.WeChatMPPublisher
    login_qrcode_selector: "#login-qrcode"
    cookie_file: "wechat_cookies.json"
```

**权衡**：YAML配置需要校验和错误处理，相比硬编码多一层抽象，但长期维护成本更低。

### 决策3：微信公众号发布采用二维码登录 + 浏览器自动化

**决定**：利用Playwright模拟微信公众号后台登录，通过二维码扫码完成身份验证，后续发布操作也完全自动化。

**备选方案**：寻找非官方API或第三方SDK。

**原因**：
- 微信官方没有提供文章发布的公开API，任何第三方API都有被封禁风险。
- 二维码登录是微信公众号后台的唯一官方登录方式，模拟浏览器是最直接的方案。
- Cookies缓存机制允许在首次扫码后长时间免登录。

**权衡**：首次启动需要人工扫码，破坏了“完全无人值守”的愿景。但结合邮件或钉钉通知，可由运维人员在启动时远程扫码一次，后续自动。

## 💡 关键收获

1. **浏览器自动化是API退化的最后防线，但代价不容忽视**：当官方API不可用时，Playwright这类工具提供了回退方案。但需要投入大量精力处理动态DOM、事件冒泡、认证流程。对于CSDN编辑器，仅选择器调试就耗费了超过4个小时。因此建议：优先争取API，Browser Automation是“最后一公里”的备用方案。

2. **Cookie缓存是自动化管线的“免签护照”**：无论是CSDN还是微信公众号，每次启动都重新登录会引入人为等待和失败点。将登录后的Cookies序列化存储，并处理其过期逻辑，可以大幅提升自动化率。我们的经验是设置一个健康检查：在加载Cookies后尝试访问受限页面，若返回登录页则触发重新认证。

3. **版本锁定与向后兼容不可忽视**：Claude Code的日志格式变更提醒我们，任何依赖外部工具的版本更新都可能带来兼容性问题。对于关键的数据捕获和集成点，应当：① 官方发布变更日志时及时测试；② 实现支持新旧两种格式的适配器（adapter）；③ 考虑用版本锁`~/.claude/version`或Docker来固定工具版本。

今天的开发验证了多平台发布的可行性，同时也提醒我们：真实世界中的接口与实现总是在迭代，保持代码的灵活性和错误恢复能力比追求完美更关键。
