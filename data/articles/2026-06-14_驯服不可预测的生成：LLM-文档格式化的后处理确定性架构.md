在构建 `ai-developer-knowledge-hub`的过程中，我们发现了一个所有 Agent 系统迟早都会面临的 "脏数据" 问题：LLM 生成的文档虽然语义丰富，但在格式上简直是一场灾难。代码块语言标签缺失、列表嵌套混乱、多余的空行充斥全文，这些看似微小的瑕疵累积起来，直接摧毁了文档的可维护性。

今天，我们不谈 Prompt Engineering 如何优化输出（那是个无底洞），而是聊聊如何通过在 Pipeline 中引入确定性的后处理层，以架构级的手段解决非确定性模型的输出一致性难题。

```### 1. Background & Problem

我们的系统每天通过 Agent 自动生成大量的技术文档。初期，我们寄希望于通过精心设计的 System Prompt 来约束输出格式。我们尝试过诸如 "Use strict markdown syntax"、"Ensure all code blocks have language tags" 等指令，甚至使用了 Few-Shot Examples。

### 然而，现实是残酷的。

即使是最先进的 GPT-4 或 Claude 3.5 Sonnet，在处理复杂上下文时，偶尔也会 "偷懒" 或产生格式漂移。具体表现为：

1. **代码块语言缺失**：渲染出的代码没有高亮，影响阅读体验。
2. **列表层级错乱**：有时将`-`混用为`*`，或者缩进不符合 Markdown 规范。
3. **空白爆炸**：段落之间出现 3-4 个空行，浪费垂直空间。

如果你正试图把 LLM 输出直接塞进生产环境的 CMS 或静态站点生成器（如 Hugo/VitePress），这种不一致性会导致构建失败或排版崩坏。

### 2. Root Cause Analysis

为什么 Prompt Engineering 失效了？**因为我们在试图用概率性的模型解决确定性的需求。**LLM 的本质是下一个 token 预测器。虽然它 "学过" Markdown 语法，但在生成过程中，它优先关注的是语义的连贯性，而不是语法的严格性。当 Token 预测的概率分布在 "空格" 和 "换行" 之间差别微小时，模型就会表现出随机性。

```mermaid

### 3. Solution Deep Dive

### 核心思路：将 "内容生成" 与 "格式规约" 解耦。

我们不再要求 LLM 输出完美的格式，而是要求它输出 "可读的、语义正确的 Markdown"。随后，我们引入了一个 Python 编写的`FormatSanitizer`工具，作为 Pipeline 的必经环节。这个工具不关心内容的好坏，只关心结构的规范性。

我们选择了`markdown-it-py`库而非简单的正则表达式。为什么？因为正则无法处理嵌套结构（比如列表中的代码块）。我们需要将 Markdown 解析为抽象语法树（AST），操作 AST 后再重新序列化。

#### The Code: Sanitizer Implementation

以下是生产级 Sanitizer 的核心实现片段。它展示了如何通过 AST 遍历来修复代码块和列表问题：```python
import markdown_it
from markdown_it.tree import SyntaxTreeNode

class MarkdownSanitizer:
    def __init__(self):
# 初始化 markdown-it parser，配置严格模式
        self.md = markdown_it.MarkdownIt()

    def sanitize(self, raw_text: str) -> str:
        """主入口：解析 -> 遍历修复 -> 渲染"""
        if not raw_text:
            return ""

# 解析为 AST
        tokens = self.md.parse(raw_text)
        root_node = SyntaxTreeNode(tokens)

# 递归遍历修复树结构
        self._traverse_and_fix(root_node)

# 重新渲染为标准 Markdown
        return self._render_node(root_node)

    def _traverse_and_fix(self, node: SyntaxTreeNode):
        """深度优先遍历，应用格式化规则"""

# 规则 1: 修复代码块语言标签
        if node.type == "fence":
            info = node.info.strip() if node.info else ""
            if not info:
# 尝试根据内容猜测语言，或者默认为 text
                node.info = "text"
            else:
# 规范化语言名称（如 js -> javascript）
                node.info = self._normalize_lang(info)

# 规则 2: 规范化列表样式
        if node.type == "bullet_list":
# 强制所有子项的标记为 '-'
            for child in node.children:
                if child.type == "list_item":
# 修改内部 text node 的 marker
                    child.map = child.map # 保持位置映射

# 规则 3: 清理多余空行（软换行）
        if node.type == "paragraph":
# 将连续的 softbreak 合并
            self._dedup_softbreaks(node)

# 递归处理子节点
        for child in node.children:
            self._traverse_and_fix(child)

    def _normalize_lang(self, lang: str) -> str:
        """映射常见的简写到标准名"""
        lang_map = {
            "py": "python",
            "js": "javascript",
            "ts": "typescript",
            "sh": "bash",
            "yaml": "yml"
        }
        return lang_map.get(lang.lower(), lang.lower())

    def _render_node(self, node: SyntaxTreeNode) -> str:
        """简化版渲染器，实际生产中可以使用更健壮的序列化逻辑"""
# 这里为了展示简洁省略了详细的序列化代码
# 实际实现需根据 AST 结构拼接字符串
        return node.to_markdown()
```#### Integration Pattern

我们将这个工具集成到了 Agent 的执行循环末尾，在 commit 动作之前：```python
# Agent Workflow Pipeline
def run_generation_pipeline(task: Task):
# 1. Context Gathering (RAG)
    context = knowledge_base.retrieve(task.topic)

# 2. LLM Generation (Non-Deterministic)
    raw_content = llm_client.generate(
        system_prompt="Generate technical docs. Focus on accuracy.",
        user_context=context
    )

# 3. Deterministic Sanitization (The Guardrail)
    sanitizer = MarkdownSanitizer()
    clean_content = sanitizer.sanitize(raw_content)

# 4. Validation & Commit
    if validate_structure(clean_content):
        git_repo.commit(path=task.path, content=clean_content)
    else:
        raise PipelineError("Sanitization failed validation")
```### 4. Architecture Decision Record

| Decision | Alternative | Why chosen |
|----------|-------------|------------|
| **Post-Processing Sanitizer** | Complex Prompt Engineering / JSON Mode | **Sanitizer**提供了 100% 的确定性。Prompt Engineering 依然会有偶发错误；JSON Mode 虽然结构强，但限制了 Markdown 的表达能力，不适合长文本文档。 |
| **AST-based Parsing (markdown-it)** | Regex / String Replacement | **AST** 能正确处理嵌套。正则无法区分代码块里的 "*"（注释）和 Markdown 的 "*"（列表），容易误伤内容。 |
| **Separate Service/Module** | Inline Function in Agent | **Module**便于独立测试和版本迭代。格式规则是会变的，将其隔离符合开闭原则。 |

### 5. Production Considerations

在上线这个架构后，我们观察到了几个关键点，这也是面试中能体现你 Senior 级别的细节：

1.**性能开销**：Sanitizer 是纯 CPU 密集型操作。对于 5KB 的文档，处理耗时约 15ms。相比 LLM 的 2-5s 生成时间，这个开销几乎可以忽略不计（<1%）。因此我们选择同步处理，无需引入消息队列异步化。

2. **回退机制**：如果 Sanitizer 抛出异常（例如解析遇到极度畸形的 Markdown），我们不会直接挂死 Pipeline。策略是将 "Raw Markdown" 原样存入，并打上一个`needs_review`的 Tag，触发人工介入。宁可要 "脏" 内容，也不要丢失数据。

3. **可观测性**：我们在 Sanitizer 中埋点了`format_corrections_count` 指标。
   -   *P50 correction count: 2* (大多数情况下只是修几个空格)
   -   *P99 correction count: 45* (偶尔 LLM 发疯，Sanitizer 挽救了大量格式错误)
   这个指标如果突然飙升，通常意味着 LLM Provider 更新了模型或者 Prompt 需要调整。

### 6. Key Takeaways

1.  **拥抱非确定性，但管理接口**：不要试图驯服 LLM 的随机性，而是在它和你的下游系统之间建立一道确定性防火墙。Post-processing 往往比 Pre-prompting 更有效、更便宜。

2.  **AST > Regex**：处理结构化文本（Markdown, HTML, Code）时，永远不要依赖正则。解析为 AST 是唯一的正道，它能保证你修改的是 "语法结构" 而不是 "文本片段"。

3.  **关注 P95 的体验**：虽然大多数时候 LLM 输出尚可，但 P95 的格式错误会破坏用户信任。Sanitizer 确保了最坏情况下的质量底线。

4.  **架构解耦的价值**：将 Formatting 逻辑剥离出来，使得我们可以随时升级格式规范（比如从 CommonMark 迁移到 GFM），而无需重新训练 Agent 或修改 Prompt。
