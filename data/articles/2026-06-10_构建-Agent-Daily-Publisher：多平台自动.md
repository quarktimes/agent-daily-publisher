## 🔧 问题和方案

### 三层隐私防护体系：防止敏感信息泄露

**背景**：
在构建自动化技术博客发布系统时，一个核心风险在于 AI 生成的内容可能包含开发环境的敏感数据（如数据库连接串、API Key 等）。如果直接将生成的 Markdown 发布到公网平台，会导致严重的安全事故。

**根因分析**：
敏感数据泄露可能发生在三个阶段：
1.  **代码提交阶段**：开发者误将包含密钥的配置文件写入 Git 仓库。
2.  **内容生成阶段**：LLM 在总结日志或分析代码时，将读取到的 `spring.datasource.password` 等配置信息直接写入生成的文章文本中。
3.  **发布验证阶段**：发布前缺乏最后一道防线，未能检测到文本中残留的敏感字段。

**方案**：
我们实施了“纵深防御”策略，在三个关键节点部署了防护措施：

1.  **Pre-commit Hooks**：利用 Git 钩子在代码提交前扫描待提交文件，检测类似 `password=`、`api_key=` 等敏感模式。
    ```bash
    # .git/hooks/pre-commit 示例逻辑
    if git diff --cached --name-only | xargs grep -i "password="; then
      echo "WARNING: Potential secret detected!"
      exit 1
    fi
    ```
2.  **输入清洗**：在调用 LLM 生成文章之前，对输入的日志或代码片段进行正则替换，将敏感值脱敏。
3.  **输出校验**：在文章生成后、发布前，再次扫描生成的 Markdown 文本，确保不包含 `jdbc:mysql://` 或 `sk-xxxx` 等特征。

**效果**：
成功建立了自动化的安全审计流程，确保即便输入源包含敏感信息，发布到公网的内容也是经过清洗的，消除了凭据泄露的风险。

### 微信公众号 IP 白名单限制的绕过方案

**背景**：
微信公众号（WeChat MP）官方提供了素材管理接口，理想情况下应通过 API 直接发布文章。但在实际对接中，我们遇到了网络访问限制。

**根因分析**：
微信公众号的 API 调用要求服务器的 IP 地址必须在后台配置的白名单中。对于本地开发环境或动态 IP 的云部署环境（如 GitHub Actions、动态 ECS），维护一个固定的 IP 白名单不仅运维成本高，而且在某些网络环境下（如 CSDN 访问受限）根本不可行。API 的严格网络策略与自动化系统的灵活性需求产生了冲突。

**方案**：
我们决定放弃纯 API 发布，转而采用**浏览器自动化**方案（使用 Playwright 或 Selenium）。

同时，为了平衡效率与安全性，我们设计了“草稿 API + 人工发布”的混合模式：
1.  利用浏览器自动化模拟登录后台，上传图片并排版（解决 CSDN 无 API 的问题）。
2.  对于微信公众号，先通过 API 创建草稿，保留人工最终审核发布的环节。

```python
# 伪代码示例：切换到浏览器自动化模式
if platform == "WeChat MP" and not is_ip_whitelisted():
    publisher = BrowserAutomationPublisher(headless=True)
else:
    publisher = APIPublisher(api_key=config.get_key())
```

**效果**：
彻底解决了 IP 白名单的限制问题，使得系统能够在任何网络环境下运行。虽然浏览器自动化的速度比 API 慢（约 15-30秒/篇 vs <1秒/篇），但它提供了与人工操作一致的兼容性，且避免了复杂的网络运维工作。

### 修复 Claude Code 历史日志读取器

**背景**：
我们的 Daily Reporter 依赖 Claude Code 的本地历史文件（`~/.claude/history.jsonl`）来生成每日工作摘要。但在测试中发现，最新的会话记录无法被读取。

**根因分析**：
原代码在解析 JSONL 文件时，存在两个缺陷：
1.  未能正确处理文件流的重置，导致只读取了旧缓存。
2.  日期过滤逻辑时区处理不当，导致当天的新会话被误判为“未来”或“过去”而被过滤掉。

**方案**：
重写了日志解析模块，显式处理文件指针，并统一了时区标准。
```python
# 修复后的核心逻辑
with open(history_path, 'r', encoding='utf-8') as f:
    for line in f:
        session = json.loads(line)
        session_time = parse_date(session['timestamp'])
        if is_within_target_date(session_time, target_date):
            valid_sessions.append(session)
```

**效果**：
恢复了日报生成的准确性，确保当天的 AI 对话能够实时转化为博客素材。

## 🏗 架构决策

### 混合发布架构：API 与浏览器自动化的取舍

**决策内容**：
在系统设计中，我们没有对所有平台统一使用 API 或统一使用浏览器自动化，而是选择了**混合策略**：Dev.to 使用 API，CSDN 和微信使用浏览器自动化（或辅助 API）。

**考量过的替代方案**：
1.  **全 API 方案**：所有平台均调用官方接口。这是最稳定、性能最好的方案，但受限于平台开放程度（CSDN 无公开 API）和网络策略（微信 IP 白名单）。
2.  **全浏览器自动化方案**：模拟人工操作所有流程。这是通用性最强的方案，但维护成本极高，页面 DOM 结构的任何变动都会导致发布失败。

**最终选择理由**：
Dev.to 拥有极佳的 API 支持且无网络限制，理应享受 API 的高效与稳定；而 CSDN 和微信受限于各自的封闭性或安全策略，只能“退而求其次”使用浏览器自动化。这种“能用 API 绝不用浏览器”的原则，在保证功能覆盖的同时，最大化了系统的整体稳定性。

### 三层隐私防护的架构落地

**决策内容**：
将隐私防护不仅仅作为一个代码检查工具，而是作为架构的核心组成部分，贯穿从开发到发布的全生命周期。

**考量过的替代方案**：
仅在发布前做一次正则匹配检查。虽然这能拦截大部分泄露，但无法防止源代码仓库被污染，也无法解决 LLM 训练数据可能包含敏感信息的问题。

**最终选择理由**：
安全领域没有银弹。多层防护能够在某一层失效时提供冗余保护。Pre-commit hook 保护了代码库安全，输入清洗保护了生成过程，输出校验保护了发布结果。这种架构虽然增加了少量复杂性，但对于处理敏感数据的自动化系统来说是必须的投资。

## 💡 关键收获


1.  **IP 白名单是自动化系统的隐形枷锁**：在设计依赖第三方 API 的系统时，必须提前调研网络准入策略。对于动态 IP 环境（如 Serverless 或 CI/CD），如果对方强制 IP 白名单，浏览器自动化往往是唯一的解耦方案。

2.  **自动化发布中的隐私防线必须“纵深”**：不要信任单一的数据清洗步骤。敏感信息可能隐藏在 JSON 配置中、Shell 脚本里，甚至被 AI 重新编码进 Base64 字符串中。只有在输入、处理、输出三个环节都设卡，才能确保万无一失。

3.  **人工介入是自动化流程的安全阀**：在微信公众号的发布流程中，我们特意保留了“API 生成草稿 -> 人工审核发布”的环节。完全的无人值守发布虽然效率高，但在内容质量不可控或风险较高时，保留“人机回环”是避免灾难性错误的最佳实践。

4.  **环境变量管理是基础设施的地基**：今天我们在配置 Dev.to 和微信凭据时，再次确认了将敏感信息写入环境变量并纳入 `.gitignore` 的重要性。任何硬编码在代码中的凭据，最终都会成为泄露的源头。
