# 驯服不可控的 LLM 输出：在知识库构建中引入确定性后处理层

Date: 2026-06-14

## 架构概览

在构建企业级 AI 知识库时，我们面临的核心矛盾是：**大语言模型（LLM）的创造性与文档工程所需的严格规范性之间的冲突**。为了解决这一问题，我们在生成管道中引入了一个确定性后处理层。

```mermaid

    subgraph "Generation Phase (Stochastic)"
        A[User Query] --> B[LLM Orchestrator]
        B --> C[RAG Retrieval]
        C --> B
        B --> D[Raw Markdown Output]
    end

    subgraph "Sanitization Phase (Deterministic)"
        D --> E[Format Sanitizer]
        E -->|Regex Parsing| F[Structure Normalizer]
        F -->|AST Rewriter| G[Whitespace Cleaner]
        G --> H[Publish-Ready Doc]
    end

    H --> I[Knowledge Hub Vector DB]
```## 1. 背景与问题

我们在维护`ai-developer-knowledge-hub`项目时遇到了一个典型的“熵增”问题。随着知识库文档数量的增加，文档风格的混乱程度呈指数级上升。具体表现为：

-   **代码块格式混乱**：有的缺少语言标识符（只有` ``` `而没有` ```java `），导致高亮失效；有的缩进不一致。
-   **列表结构变异**：在长上下文中，LLM 经常混用有序列表（`1.`）和无序列表（`-`），甚至在同一个列表层级中切换风格。
-   **冗余空白**：生成的内容中夹杂着不规则的换行符和多余的空格，这在渲染到 Web 端时会造成布局崩坏。

这不仅仅是美观问题。对于开发者知识库而言，**代码块缺少语言标识符会直接破坏语义检索的质量**——向量模型无法准确识别代码上下文，导致后续的 RAG（检索增强生成）召回率下降。

## 2. 根本原因分析

为什么仅仅优化 Prompt 无法解决这个问题？我们需要深入到 LLM 的生成机制。

```mermaid

    participant User
    participant Orchestrator
    participant LLM
    participant PromptEng

    User->>Orchestrator: Generate Doc for Topic X
    Orchestrator->>PromptEng: Fetch System Prompt
    PromptEng-->>Orchestrator: "Use strict markdown..."
    Orchestrator->>LLM: Send Prompt + Context

    Note over LLM: Temperature=0.7<br/>Stochastic Sampling
    LLM->>LLM: Token by Token generation
    LLM-->>Orchestrator: Raw Tokens

    Orchestrator->>Orchestrator: Decode to String

    alt Pattern Drift Detected
        Orchestrator-->>User: Inconsistent Markdown
    end
```问题的根源在于 LLM 的生成本质是**概率性的**。即使我们在 System Prompt 中写入“必须使用严格的 Markdown 格式”，LLM 也只是在训练数据的概率分布下进行“模仿”。当上下文很长或涉及到多个代码块切换时，Attention 机制可能会“遗忘”之前的格式约束，导致输出漂移。

此外，Prompt 优化存在边际效应递减。为了覆盖所有边缘情况，Prompt 会变得极其冗长，不仅增加了 Token 成本和推理延迟，还可能因为指令冲突导致模型困惑。**Prompt 是“软约束”，而代码层面的后处理是“硬约束”**。在工程实践中，我们不能依赖模型来遵守它并不真正“理解”的语法规则。

## 3. 解决方案深度剖析

我们的解决方案是构建一个独立的`format_sanitizer.py`模块，将其插入到`daily_pipeline.py`的 LLM 生成步骤之后、入库步骤之前。这是一个经典的 **“Pipe-and-Filter”** 架构模式的应用。

### 核心实现：Python AST 级别的清洗

我们不仅使用了正则表达式（Regex）进行快速修复，还引入了简单的抽象语法树（AST）逻辑来处理嵌套结构。以下是核心代码片段的演进。

### Before: 依赖 Prompt 祈祷```python

### After: 引入 FormatSanitizer 确定性处理
```python
import re
from typing import List, Optional

class FormatSanitizer:
    def __init__(self):
# 匹配未指定语言的代码块:```\ncontent\n
```text
self.code_block_pattern = re.compile(r'
```
\n([\s\S]*?)\n```')
# 匹配非标准的列表符号
        self.list_pattern = re.compile(r'^\s*(\d+\.|-|\*)\s+', re.MULTILINE)

    def sanitize(self, raw_markdown: str) -> str:
        """
        执行确定性清洗流程：代码块修复 -> 列表归一化 -> 空白清理
        """
# 1. 代码块语言推断与补全
        processed = self._fix_code_blocks(raw_markdown)

# 2. 列表结构标准化
        processed = self._normalize_lists(processed)

# 3. 冗余空白清理
        processed = self._clean_whitespace(processed)

        return processed

    def _fix_code_blocks(self, text: str) -> str:
        """
        查找所有代码块，如果缺失语言标识符，尝试根据内容推断
        或默认为 text。这是提升 RAG 检索效果的关键步骤。
        """
        def replacer(match):
            content = match.group(1)
# 简单的启发式推断：如果包含 'def ' 或 'class ' 则为 python
            if 'def ' in content or 'import ' in content or 'class ' in content:
                lang = 'python'
            elif 'function ' in content or 'const ' in content:
                lang = 'javascript'
            elif 'public class ' in content:
                lang = 'java'
            else:
                lang = 'text'
            return f'```{lang}\n{content}\n```'

        return self.code_block_pattern.sub(replacer, text)

    def _normalize_lists(self, text: str) -> str:
        """
        将列表项统一为 '- ' 格式，处理混用情况。
        注意：这里简化了处理，生产环境可能需要处理嵌套层级。
        """
        lines = text.split('\n')
        normalized_lines = []
        for line in lines:
            match = self.list_pattern.match(line)
            if match:
# 提取缩进和内容，统一替换为 '- '
                indent = len(line) - len(line.lstrip())
                content = line[match.end():]
                normalized_lines.append(' ' * indent + '- ' + content)
            else:
                normalized_lines.append(line)
        return '\n'.join(normalized_lines)

    def _clean_whitespace(self, text: str) -> str:
        """
        清除多余的空行（超过2个连续换行）
        """
        return re.sub(r'\n{3,}', '\n\n', text).strip()

```text
### 集成到 Pipeline

我们将上述逻辑封装为一个可复用的组件，并集成到主流程中。
```python
# daily_pipeline.py integration
from format_sanitizer import FormatSanitizer

def run_daily_generation_job():
# ... RAG retrieval and LLM generation ...
    raw_content = llm.generate(context, prompt)

# The Critical Step: Post-processing
    sanitizer = FormatSanitizer()
    clean_content = sanitizer.sanitize(raw_content)

# 只有通过清洗的内容才会被入库
    if validate_markdown_structure(clean_content):
        knowledge_hub.publish(clean_content)
    else:
        alert_team("Sanitizer failed to fix structure, manual review needed")```**设计决策点**：为什么选择 Python 脚本而不是 LLM Function Calling 来完成清洗？
使用 LLM 自我修正不仅成本高昂（消耗额外的 Token），而且容易引入新的幻觉。传统的代码逻辑是 **O(N)**确定性的，既快又准，适合处理结构化格式问题。

## 4. 架构决策记录 (ADR)

| 决策 | 替代方案 | 选择理由 |
|------|----------|----------|
| **确定性后处理层** | 1. 仅依赖 Prompt Engineering<br>2. 另一个 LLM Agent 进行“Reviewer”模式 | Prompt 的软约束无法保证 100% 合规；LLM Reviewer 成本高且速度慢。确定性代码逻辑最符合工程化要求，虽牺牲了一定灵活性，但换取了 100% 的格式一致性。 |
| **启发式语言推断** | 默认标记为`text`或`unknown` | 对于 RAG 系统，代码块的语言标识至关重要。简单的启发式规则覆盖了 80% 的常见场景，显著提升了向量索引的质量。 |
| **独立模块** | 将清洗逻辑直接写在 Pipeline 主脚本中 | 遵循单一职责原则（SRP）。清洗逻辑可能需要频繁调整（例如增加新的格式规则），独立模块便于单元测试和维护。 |

## 5. 生产环境考量

引入这一层后，我们需要关注以下工程指标：

-**延迟**：清洗逻辑是正则操作，对于 2KB-5KB 的文档，处理耗时通常在 **5ms - 15ms**之间，这与 LLM 的**2s+**生成时间相比是可接受的（<1% 开销）。
-**鲁棒性**：如果后处理脚本本身解析失败（例如遇到极度畸形的 Markdown），必须有熔断机制。我们的实现是：如果正则抛出异常，回退到原始内容并记录 Error Log，而不是阻塞整个 Pipeline。
-   **可观测性**：我们在清洗步骤中增加了 Prometheus 指标，例如`sanitizer_fixed_blocks_total`和`sanitizer_inferred_lang_python`。这能帮助我们监控 LLM 的输出质量趋势——如果“修复率”突然飙升，可能意味着上游模型漂移或 Prompt 被意外修改。

### 何时不应使用此方案？
如果你的应用场景是创意写作或聊天机器人，过度的格式标准化会破坏输出的“人味”和自然流畅度。但在知识库、API 文档生成、代码解释等场景下，标准化是必须的。

## 6. 关键要点

1.  **将“内容生成”与“格式化”解耦**：不要让 LLM 做它不擅长的事情（严格遵守语法）。利用传统的确定性代码来补齐 LLM 的短板。
2.  **Prompt 是建议，代码是法律**：在系统架构中，对格式、校验等强一致性要求，永远要依赖代码层面的硬约束。
3.  **后处理层是 RAG 的隐形助推器**：规范化的 Markdown（特别是代码块语言标识）能大幅提升切片质量和向量检索的准确率，这往往是容易被忽视的 RAG 优化点。
4.  **监控修复率**：把后处理工具的修复频率作为衡量上游 LLM 输出稳定性的重要指标。

通过引入 `format_sanitizer`，我们将知识库的文档混乱度从“不可用”降低到了“企业标准”，实现了真正的自动化内容工厂。
