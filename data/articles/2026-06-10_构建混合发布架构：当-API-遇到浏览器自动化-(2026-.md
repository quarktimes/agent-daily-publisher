# 构建混合发布架构：当 API 遇到浏览器自动化 (2026-06-10)

## 📌 今日概述

今天主要完成了 Agent Daily Publisher 项目的核心开发工作，构建了一套支持多平台的自动化发布管线。我们不仅实现了基于 API 的发布（如 Dev.to），还针对缺乏 API 的平台（如 CSDN、微信公众号）引入了 Playwright 浏览器自动化方案，同时完善了隐私过滤机制并将项目部署至 GitHub。

## 🔧 问题和方案

### 1. Claude Code 历史记录读取失败

**背景**
在尝试从 Claude Code 的会话历史中提取数据生成日报时，`claude_log_reader.py` 无法读取到任何条目，导致管线生成的文章内容为空。

**根因分析**
Claude Code 更新了其数据存储格式。原先的解析器基于旧的格式设计，而新版 Claude Code 已将历史记录迁移为 JSONL（JSON Lines）格式，存储在 `~/.claude/history.jsonl` 中。此外，真正的详细会话内容被分散存储在 `~/.claude/sessions/` 目录下的独立文件中，旧的读取逻辑未能适配这一结构变化。

**方案**
更新了 `claude_log_reader.py` 的解析逻辑，改为逐行读取 JSONL 格式，并根据 `history.jsonl` 中的索引信息去 `sessions/` 目录读取具体的会话详情。

```python
# 伪代码示例：新的 JSONL 解析逻辑
import json

with open(history_file_path, 'r') as f:
    for line in f:
        session_entry = json.loads(line)
        # 提取 session_uuid 并读取对应的 sessions/uuid 文件
        session_data = load_session_file(session_entry['uuid'])
        process_session(session_data)
```

**效果**
修复后，管线成功提取了 2026-06-10 的 1 条记录和 2026-06-09 的 2 条记录，日报生成流程恢复正常。

### 2. Dev.to 发布失败：标题与标签格式错误

**背景**
在向 Dev.to 平台发布文章时，请求返回错误，提示标题验证失败且标签格式不正确，导致发布流程中断。

**根因分析**
经过排查发现两个问题：一是 Payload 结构中的标签格式不符合 Dev.to API 要求（未正确序列化为数组字符串）；二是 `core/agent.py` 中对 Agent 输出的标题验证逻辑过于严格，误拦截了合法的标题格式。

**方案**
修改 `devto.py` 中的标签处理逻辑，确保标签数组被正确序列化；同时优化 `core/agent.py` 的结构化输出校验，放宽对标题的正则匹配规则。

```python
# 修正后的 Payload 结构示例
payload = {
    "article": {
        "title": article_data['title'],
        "body_markdown": article_data['content'],
        "tags": [tag.strip() for tag in article_data['tags'].split(',')] # 确保是列表
    }
}
```

**效果**
成功将 2026-06-08 和 2026-06-09 的文章发布至 Dev.to 平台，API 交互稳定。

### 3. CSDN 与微信公众号无 API 接入

**背景**
项目目标是实现多平台自动发布，但 CSDN 开放平台已无法访问，而微信公众号必须通过扫码登录，两者均未提供可编程的发布 API。

**根因分析**
国内部分平台出于生态闭环或反爬虫考虑，不对外开放内容发布的 API 接口。这导致纯 HTTP 请求的方式无法完成发布操作。

**方案**
采用浏览器自动化技术作为补充方案。引入 Playwright 库，创建了 `browser_base.py` 基础抽象类，并实现了 `csdn_browser.py` 和 `wechat_browser.py`。

- **CSDN**: 针对 `contenteditable` 编辑器，模拟键盘输入（`Meta+A` 全选后粘贴）以绕过直接 DOM 操作的限制。
- **微信**: 自动化登录流程（需人工介入扫码一次），并定位到文章编辑器的 DOM 节点进行内容注入。

```python
# CSDN 浏览器发布核心逻辑示例
async def publish_to_csdn(page, title, content):
    await page.goto('https://mp.csdn.net/mp_blog/creation/editor')
    # 定位标题输入框
    await page.fill('input[placeholder="请输入文章标题"]', title)
    # 定位正文编辑器（contenteditable）
    editor = await page.query_selector('.editor-content')
    await editor.click()
    # 模拟全选粘贴，避免复杂的富文本格式问题
    await page.keyboard.press('Meta+A')
    await page.keyboard.type(content)
    await page.click('button.publish-btn')
```

**效果**
打破了 API 限制，成功实现了对无 API 平台的自动化覆盖，虽然速度比 API 慢，但显著扩展了系统的适用范围。

### 4. 隐私安全与敏感数据过滤

**背景**
自动化生成和发布的内容可能包含开发过程中的敏感信息（如 API Key、数据库连接串等），存在泄露风险。

**根因分析**
在开发初期，部分配置硬编码在代码中，且缺乏自动化的审查机制，容易导致敏感信息随 Git 提交或公开发布的文章流出。

**方案**
实施了多层防御策略：
1. **代码层面**：将所有硬编码的凭证移至环境变量，通过 `os.getenv()` 读取。
2. **工具层面**：开发 `privacy_filter.py`，利用正则表达式扫描待发布的文章，拦截类似 `jdbc:mysql://`、`password=` 等敏感模式。
3. **流程层面**：在 `daily_pipeline.py` 中集成隐私过滤作为必经阶段，并添加 `pre-commit-check.sh` Git 钩子，防止提交包含敏感数据的文件。

**效果**
建立了一套完整的“深度防御”体系，确保无论是生成的文章还是 Git 仓库，都不会包含明文凭证。

## 🏗 架构决策

### 1. 混合发布策略：API + 浏览器自动化

**决策内容**
针对不同平台的能力差异，决定采用混合架构：有 API 的平台（Dev.to）优先使用 HTTP API；无 API 的平台（CSDN、微信）回退到 Playwright 浏览器自动化。

**备选方案**
- 仅支持有 API 的平台（放弃 CSDN 和微信）。
- 全部使用浏览器自动化（放弃性能优势）。

**决策理由**
API 方式速度快、稳定性高、资源消耗低；浏览器自动化虽然慢且易受 UI 变化影响，但能覆盖重要的长尾平台。混合策略在保持核心性能的同时，最大化了内容分发的触达率。

### 2. Publisher 抽象层设计

**决策内容**
定义 `Publisher` 基类（或接口），强制要求实现 `publish()` 方法。`devto.py` 继承基类并实现 HTTP 调用，`csdn_browser.py` 和 `wechat_browser.py` 继承并实现 Playwright 逻辑。

**备选方案**
在 Pipeline 中直接写 `if-else` 判断平台类型并调用不同逻辑。

**决策理由**
开闭原则。通过抽象层，Pipeline 的核心逻辑无需关心底层是 API 还是浏览器。未来新增平台时，只需新增一个 Publisher 实现类，无需修改 Pipeline 代码，降低了维护成本。

### 3. Git 策略：保留生成文章，排除原始数据

**决策内容**
在 `.gitignore` 中配置排除 `data/` 目录（包含原始会话 JSONL 和中间数据），但保留生成的 Markdown 文章。

**备选方案**
- 排除所有生成内容，保持仓库精简。
- 提交所有数据，确保完全可复现。

**决策理由**
生成的文章是系统的最终输出，保留它们可以作为效果展示和示例，增加项目的透明度。而原始数据不仅体积大，还可能包含未被过滤器的敏感信息，且对普通贡献者无价值。通过 Privacy Filter 的二次保障，保留文章是安全的。

## 💡 关键收获

1. **外部依赖的数据结构是不稳定的**
Claude Code 从旧格式迁移到 JSONL 的经历提醒我们，在解析第三方应用的本地数据时，必须预留版本检测或多格式兼容的逻辑。依赖特定文件结构是非常脆弱的，未来应考虑增加格式自动探测机制。

2. **浏览器自动化是 API 缺失时的有效补位**
尽管 Selenium 或 Playwright 比 API 慢且脆弱，但在面对“围墙花园”式的平台时，它是唯一可行的工程化方案。对于国内开发者来说，掌握浏览器自动化技术是打通自动化闭环的关键技能。

3. **隐私安全必须内建到管线中**
不能指望开发者手动检查敏感信息。将 Privacy Filter 作为 Pipeline 的必经阶段，并配合 Git Pre-commit 钩子，构建了“代码-发布-版本控制”全链路的安全网。这种“默认安全”的设计思想比事后补救更有效。

4. **抽象层是应对复杂度的利器**
通过 `browser_base.py` 和 API 发布器的一致接口设计，我们成功地将极其不同的技术手段（HTTP 请求 vs 模拟用户操作）封装在统一的接口之下。这种设计模式使得混合架构在代码层面保持了整洁和可维护性。
