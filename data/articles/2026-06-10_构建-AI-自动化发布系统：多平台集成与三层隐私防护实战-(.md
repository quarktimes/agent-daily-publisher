## 🔧 问题和方案

### 1. 微信公众号 API IP 白名单封禁问题

**背景**：
在对接微信公众号 API 时，发布请求频繁失败。微信公众号平台对 API 调用有严格的 IP 白名单限制，仅允许指定 IP 地址的服务器进行操作。对于运行在动态 IP 环境或云原生架构下的自动化服务，这构成了巨大的阻碍。

**根因分析**：
微信公众号的安全策略强制要求固定 IP，而我们的 CI/CD 环境或云服务提供商通常分配动态 IP，无法满足白名单硬性要求。这是一个典型的平台合规性限制与自动化灵活性之间的冲突。

**方案**：
放弃纯 API 方案，转而采用浏览器自动化作为微信公众号的发布通道。通过 Selenium 或 Playwright 模拟人工登录与发布操作，绕过 API 的 IP 校验限制。虽然增加了执行时间，但彻底解决了环境依赖问题。

```python
# 伪代码示例：选择发布策略的工厂模式
if platform == 'wechat_mp':
    # 微信公众号强制使用浏览器自动化
    return WeChatBrowserPublisher(driver)
elif platform == 'dev_to':
    # Dev.to 使用官方 API
    return DevToApiPublisher(api_key)
```

**效果**：
成功实现了对微信公众号的无障碍发布，摆脱了特定网络环境的束缚，使得系统可以在任何支持浏览器运行的环境中工作。

### 2. Claude Code 历史日志格式不兼容

**背景**：
Agent 依赖读取 Claude Code 的本地历史日志来生成每日技术总结。在系统升级过程中，日志读取器频繁抛出解析异常，导致无法生成内容。

**根因分析**：
Claude Code 在版本 v2.1.143+ 中调整了其日志文件的底层存储格式，从旧的纯文本或旧版 JSON 结构迁移到了新的 JSON 规范。原有的硬编码解析逻辑无法识别新结构中的关键字段，导致读取失败。

**方案**：
重构日志解析器，使其具备版本探测能力。优先尝试新格式解析，若失败则回退到旧格式逻辑，并增加了针对 JSON 结构异常的容错处理。

```python
import json

def parse_claude_log(log_path):
    try:
        with open(log_path, 'r') as f:
            data = json.load(f)
        # 尝试提取新版格式的 entries
        return data.get('daily_entries', [])
    except json.JSONDecodeError:
        # 回退到旧版正则或解析逻辑
        return parse_legacy_format(log_path)
```

**效果**：
系统现在能够同时兼容新旧版本的 Claude Code 日志，确保了 AI 工具版本迭代不会中断自动化流水线。

### 3. AI 生成内容中的敏感信息泄露风险

**背景**：
AI 在处理技术日志、错误堆栈或配置文件片段时，可能会将 API Keys、数据库连接串等敏感信息直接写入生成的文章中。单纯依靠 AI 的“指令遵循”是不可靠的。

**根因分析**：
LLM 本质上是概率预测模型，它并不理解“保密”的语义，而是基于训练数据预测下一个 Token。如果输入数据中包含高熵字符串（如 Key），AI 极大概率会将其作为上下文的一部分复现。

**方案**：
实施了**三层隐私保护体系**：
1.  **输入清洗**：在喂给 AI 之前，使用正则和规则引擎扫描源数据，替换或脱敏敏感信息。
2.  **Prompt 注入防护**：在 System Prompt 中明确禁止输出任何 Credential 格式的内容，并设置负面约束。
3.  **输出扫描**：在文章生成后、发布前，再次扫描全文内容。一旦检测到疑似 Key 的模式（如 `sk-...`, `jdbc:mysql...`），直接阻断发布并报警。

```python
# 输出扫描层示例
SECRETS_PATTERN = re.compile(r'(password|api_key|token)\s*[=:]\s*[\'"\w]+')

def scan_for_secrets(content):
    if SECRETS_PATTERN.search(content):
        raise SecurityError("Sensitive data detected in generated content!")
    return content
```

**效果**：
建立了一道自动化的安全防火墙，将信息泄露的风险降至最低，无需人工逐字审核即可放心运行自动化发布任务。

## 🏗 架构决策

### 混合发布策略

**决策内容**：
针对不同平台采用差异化的技术通道。对于 Dev.to，使用官方 API；对于 CSDN 和微信公众号，采用浏览器自动化。

**考量的替代方案**：
-   全员 API：被否决，因为 CSDN 无公开 API，微信 API 有 IP 限制。
-   全员浏览器自动化：被否决，虽然通用性强，但稳定性差、速度慢、资源消耗高。

**最终选择理由**：
这是一种务实的“最佳可达方案”。在平台限制无法通过技术手段绕过时，退而求其次选择浏览器自动化；在 API 友好型平台上，则追求极致的性能与稳定性。这种架构平衡了自动化覆盖率与系统可靠性。

**权衡**：
维护两套发布逻辑增加了代码复杂度和测试成本，但实现了最大化的内容分发触达。

### 三层隐私防护架构

**决策内容**：
不依赖单一环节，而是构建“输入-生成-输出”全链路的隐私清洗机制。

**考量的替代方案**：
-   仅在输入端过滤：被否决，AI 可能基于上下文推断或幻觉生成虚假但看似真实的 Key。
-   仅在输出端过滤：被否决，敏感信息可能进入 AI 的上下文窗口（若使用云端 API），存在合规风险。
-   人工审核：被否决，违背自动化初衷，且容易产生审核疲劳。

**最终选择理由**：
Defense in Depth（纵深防御）原则。即便某一层失效，后续层仍能提供保护，确保系统在无人值守的状态下依然安全。

## 💡 关键收获

1.  **浏览器自动化是 API 限制的最后防线**：面对 IP 白名单、无公开 API 等硬性限制，Selenium/Playwright 依然是打通自动化的万能钥匙。虽然“笨重”，但它能模拟人类操作，这是平台最难完全封锁的接口。

2.  **AI 工具的版本迭代是自动化系统的“隐形杀手”**：Claude Code 的日志格式变更直接破坏了我们的解析器。这提醒我们，在设计依赖第三方 AI 工件的系统时，解析逻辑必须具备足够的灵活性和向后兼容性，避免因上游微小的格式调整而导致整个流水线瘫痪。

3.  **隐私保护不能依赖 AI 的“自觉”**：在处理生产数据时，必须假定 AI 会泄露所有信息。基于规则的硬性过滤（Regex + Heuristics）比 Prompt Engineering 更可靠。将安全机制建立在代码逻辑上，而非语言模型的概率预测上。

4.  **环境变量配置是安全的基础**：初始化 Git 仓库时的 `.gitignore` 配置至关重要。确保任何包含 `database credentials`、`API key` 或 `internal IP` 的配置文件在提交前就被排除，是防止秘密泄露的第一道关口。
