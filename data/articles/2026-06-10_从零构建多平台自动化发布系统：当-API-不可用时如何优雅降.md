## 📌 今日概述

今天我们完成了一个端到端的多平台博客发布管道，能够自动抓取 Claude Code 会话，利用 LLM 生成技术文章，并将其发布到三个目标平台。核心挑战在于处理不同平台截然不同的接口能力——从标准的 REST API 到完全没有 API 的情况。我们实现了一套混合发布策略，结合了 API 调用和 Playwright 浏览器自动化，并构建了包含 .gitignore、pre-commit hooks 和运行时过滤的三层隐私防护机制。

## 🔧 问题和方案

### 1. 平台接口差异导致的发布障碍

**背景**：
在构建统一发布管道时，我们面临一个现实问题：目标平台的开放程度参差不齐。Dev.to 提供了完善的 REST API，但 CSDN 和微信公众号（WeChat MP）要么没有公开 API，要么有严格的访问限制。

**根因分析**：
这并非技术债务，而是平台策略差异。部分平台（如 CSDN）倾向于引导用户使用其官方编辑器以增加用户粘性；而微信 API 虽然存在，但出于安全考虑，默认仅允许白名单 IP 访问，且普通开发者难以直接通过 API 完成图文发布（特别是涉及素材上传时）。

**方案**：
我们实现了一套“API 优先，浏览器降级”的混合架构。首先尝试使用 API（如 Dev.to 和微信草稿箱）；当 API 不可用或失败时，自动切换到基于 Playwright 的浏览器自动化方案。

以 CSDN 发布器为例，我们抽象了 `BrowserBase` 基类，平台只需实现 `login` 和 `publish` 逻辑：

```python
# publisher/browser_base.py (简化示意)
class BrowserBase:
    def __init__(self, headless=True):
        self.browser = playwright.chromium.launch(headless=headless)
        self.context = self.browser.new_context()

    def publish(self, title, content, tags):
        raise NotImplementedError

# publisher/csdn_publisher.py
class CSDNPublisher(BrowserBase):
    def publish(self, title, content, tags):
        page = self.context.new_page()
        page.goto("https://mp.csdn.net/mp_blog/creation/editor")
        # 模拟登录...
        # 填写标题、正文、标签...
        # 点击发布按钮...
```

**效果**：
成功打通了 CSDN 和微信的发布路径，实现了与 API 发布统一的接口调用体验，验证了浏览器自动化作为通用兜底方案的可行性。

### 2. 微信 API 的 IP 白名单限制

**背景**：
微信公众号的素材管理和文章发布 API 非常强大，但对调用环境有严格要求。我们的发布服务器在尝试通过 API 发布时遭遇了拒绝。

**根因分析**：
微信公众平台限制了 API 调用的来源 IP，必须在后台配置 IP 白名单。对于动态 IP 或家庭网络环境的服务器，这几乎是不可能满足的条件。此外，API 对文章封面图和正文长度也有严格的校验逻辑，初次尝试时因格式不符而报错。

**方案**：
我们采取了双重策略：
1. **API 模式**：用于创建草稿，允许人工审核后再发布，规避了直接发布的部分风险和限制。
2. **自动降级**：当 API 调用失败（如触发 IP 白名单错误）时，系统自动捕获异常，无缝切换到 Playwright 浏览器模拟登录发布流程。

**效果**：
即使服务器 IP 不在白名单内，发布流程依然不中断，保证了系统的鲁棒性。

### 3. 历史日志读取不完整

**背景**：
管道的数据摄取阶段需要读取 Claude Code 的 `history.jsonl` 文件来分析最近的会话。但在测试中发现，最新的几条记录总是丢失。

**根因分析**：
这是因为文件读取逻辑没有处理“活跃写入”的情况。Claude Code 正在运行的会话可能还在缓冲区，或者文件刚刚被追加但尚未完全落盘/刷新，简单的顺序读取会遗漏最新的末尾内容，或者读取到不完整的数据块。

**方案**：
优化了日志读取器，增加了文件完整性检查和重试机制，确保能够捕获包括最近写入的会话在内的所有有效条目。

**效果**：
数据摄取阶段不再遗漏新生成的会话数据，保证了文章生成的实时性。

### 4. 敏感数据泄露风险

**背景**：
LLM 生成的内容基于我们的源代码和配置文件，存在将 API Key、数据库连接字符串等敏感信息无意中包含在生成文章中的风险。同时，生成的 Markdown 文件和配置文件如果直接提交到 GitHub，后果不堪设想。

**根因分析**：
AI 生成内容的不可预测性是根因。此外，开发者在配置 `.gitignore` 时，容易因为模式过于宽泛（如直接忽略整个 `data/` 目录）而导致正常的生成内容无法被版本控制，或者因为规则遗漏导致敏感文件泄露。

**方案**：
实施了“三层防御”策略：
1. **Git 层面**：精细化 `.gitignore`，排除敏感配置（如 `.env`、`secrets/`），但允许生成的文章（`articles/*.md`）被追踪。
2. **Pre-commit Hooks**：引入 secret-scanning 工具，在提交前扫描暂存区，阻止包含潜在密钥的提交。
3. **运行时过滤**：在 LLM 生成内容后，通过正则匹配和关键词过滤，清除文章中残留的敏感信息（如 `password=`、`api_key=` 等）。

**效果**：
彻底消除了因自动化发布导致凭证泄露的隐患，保障了代码仓库的安全性。

### 5. .gitignore 配置冲突

**背景**：
在实施隐私保护时，我们曾将所有数据目录加入 `.gitignore`，导致生成的文章无法上传到 GitHub，破坏了版本追踪。

**根因分析**：
过度防御。为了不泄露原始日志文件（可能包含敏感上下文），使用了 `data/` 这一通配符，误伤了在该目录下生成的且安全的 `.md` 文章文件。

**方案**：
细化了忽略规则，仅排除原始日志和临时文件，保留最终产出物：

```gitignore
# 忽略原始数据
/data/raw_logs/
/data/temp/

# 保留生成的文章
!data/articles/*.md
```

**效果**：
既保护了敏感源数据，又实现了生成内容的版本管理。

## 🏗 架构决策

### 1. 混合发布架构 (REST API + Browser Automation)

**决策内容**：
决定不依赖单一发布方式，而是构建一个能够根据平台能力自动选择最佳发布通道的架构。

**备选方案**：
- 全 API 方案：放弃不支持 API 的平台。
- 全浏览器自动化方案：所有平台都用 Playwright 模拟。

**选择理由**：
全 API 方案覆盖面太窄；全浏览器方案虽然通用，但维护成本极高（UI 稍微变动就可能导致脚本失效）且速度慢。混合架构在稳定性和覆盖面之间取得了最佳平衡——用 API 解决 80% 的高频场景，用浏览器自动化解决剩下的长尾需求。

### 2. 微信公众号使用“草稿 API”而非“直接发布 API”

**决策内容**：
在集成微信时，优先选择调用“新增草稿”接口，而非“发布”接口。

**备选方案**：
- 直接调用发布接口，文章立即对公众可见。

**选择理由**：
虽然自动化是目标，但内容质量不能妥协。AI 生成的文章偶尔会有幻觉或格式问题。通过生成草稿，引入了“人工审核”这一环节，作为最后一道防火墙。这虽然增加了一个手动步骤，但极大地降低了发布错误内容的风险。

### 3. 三层隐私防护机制

**决策内容**：
在设计阶段就将隐私保护作为核心需求，而非事后补丁。

**备选方案**：
- 仅依赖环境变量存储密钥，不检查生成的代码。

**选择理由**：
在 AI 辅助开发中，LLM 很容易在上下文中学习到你的环境变量格式并在生成代码中“复现”它们。单点防御（如仅 .gitignore）极易失效。纵深防御是处理此类不可预测输入的唯一安全策略。

### 4. 基于阶段的管道编排

**决策内容**：
将整个流程拆解为 Gather（收集）、Capture（捕获）、Analyze（分析）、Format（格式化）、Publish（发布）五个独立阶段。

**备选方案**：
- 编写一个巨大的单体脚本从头跑到尾。

**选择理由**：
模块化设计带来了极大的可测试性。如果发布失败，我们可以直接重试 Publish 阶段，而无需重新消耗 Token 进行文章生成。同时，每个阶段可以独立输出中间产物，便于调试和监控。

## 💡 关键收获

1.  **浏览器自动化是“必要的恶”**：在多平台发布场景下，面对那些没有 API 或 API 限制重重（如 IP 白名单）的平台，Playwright 这样的自动化工具是唯一解。关键在于构建良好的抽象层（如 `BrowserBase`），将平台特有的登录、DOM 操作封装起来，降低因 UI 变动带来的维护成本。

2.  **隐私设计需从 Day One 开始**：不要指望事后修补。LLM 具有记忆和模仿能力，很容易在生成的 Markdown 中混入 `jdbc:mysql://...` 或 `api_key=sk-...`。必须在生成后立即进行清洗，并在提交到 Git 前再次扫描。

3.  **降级机制提升系统韧性**：依赖第三方服务时（尤其是像微信这样的封闭生态），永远不要假设一种通道永远可用。API 挂了或权限变了怎么办？设计一套自动降级逻辑（从 API 切换到浏览器），能让你的系统在面对外部环境变化时依然保持可用。

4.  **接口隔离至关重要**：将发布逻辑抽象为统一的接口（如 `publish(title, content)`），让具体的平台适配器去处理底层差异。这样，未来如果要增加知乎、掘金等平台，只需要新增一个适配器，无需修改核心管道代码，符合开闭原则。

5.  **人工环节不可完全抹除**：尽管我们追求全自动化，但在关键链路（如内容对外发布）保留一个低摩擦的人工确认点（草稿审核），是防止灾难性错误（如批量发布垃圾内容）最具性价比的手段。
