### 1. 背景与问题：LLM 的自由散漫与工程严谨性的冲突

作为一名长期在生产环境打磨 Agent 系统的架构师，我不得不承认一个残酷的事实：LLM 的输出格式是不可信的。

上周，我们的内容生成流水线频频报警。用户反馈生成的技术文档中，代码块经常显示为纯文本，列表层级错乱，甚至偶尔会出现 Markdown 渲染器直接崩溃的情况。监控数据显示，因格式问题导致的工单占比高达 8%。对于一个标榜“自动化生产级文档”的系统来说，这是不可接受的。

问题的表象很明确：LLM 生成的 Markdown 格式极其不稳定。有时它会给代码块标注语言（如 ` ```python `），有时则忘记；有时使用 `-`作为列表符，有时混用`*`。

最初，团队的自然反应是——**优化 Prompt**。我们尝试在 System Prompt 中加入严格的格式规范，甚至给出了 Few-Shot 示例。但结果令人沮丧：格式错误的概率虽然有所下降，但并未归零。LLM 是概率模型，它理解了规则，但在生成下一个 Token 时，它依然可能“走神”。

### 2. 根因分析：Prompt 是软约束，正则是硬约束

我们陷入了误区，试图用自然语言指令（软约束）去解决一个需要严格语法匹配（硬约束）的问题。

为了彻底搞清楚问题，我抓取了 1000 条格式错误的样本进行人工分析。根因可以归纳为以下三类：

1.  **缺失语言标识**：代码块只有 ` ``` `而没有跟随`python`或`java`，导致前端高亮插件失效。
2.  **符号混用**：在同一个文档层级中，交替使用 `-`、`*`和`+`，导致某些 Markdown 解析器将其识别为不同层级的列表。
3.  **HTML 实体转义遗漏**：LLM 有时会在代码块内输出 `<`或`>`而不转义，直接破坏了 HTML 结构。

**核心洞察**：Prompt Engineering 只能提高 LLM 输出“正确格式”的概率，无法保证 100%。对于 Markdown 解析器这种零容错的下游消费者，99% 的正确率等于 0%。我们必须在 LLM 输出之后，渲染之前，引入一个确定性的后处理层。

### 3. 方案深度剖析：构建确定性 Markdown 清洗管道

既然指望 LLM 稳定输出不现实，我们就得自己动手收拾烂摊子。我设计并实现了一个`MarkdownSanitizer`管道，它的核心原则是：**凡是能用正则表达式解决的，绝不麻烦 LLM。**

### 修复 2：统一列表符号
为了兼容性，我们将所有的列表符号统一为 `-`。
```python
def unify_list_symbols(markdown_text: str) -> str:
    """
    将行首的 * 和 + 替换为 -，以保持 Markdown 风格统一。
    注意：只在列表上下文中替换（行首缩进后跟随符号）。
    """
# 匹配行首的 * 或 + (支持最多 3 层缩进)
    pattern = r"^(\s{0,3})[\*+](\s)"

    def replacer(match):
        return f"{match.group(1)}-{match.group(2)}"

# multiline=True 确保 ^ 匹配每一行的开头
    return re.sub(pattern, replacer, markdown_text, flags=re.MULTILINE)```text
### 修复 3：Save-Verify 验证循环
正则不是万能的，有时修改可能会破坏原有结构。我们引入了一个轻量级的验证循环，利用 Python 的 `markdown`库进行 parse 测试。
```python
import markdown

def verify_markdown(text: str) -> bool:
    try:
# 尝试解析 Markdown，如果抛出异常则认为格式不合法
        md = markdown.Markdown()
        md.convert(text)
        return True
    except Exception as e:
        print(f"Markdown verification failed: {e}")
        return False

def sanitize_pipeline(raw_content: str) -> str:
    current_content = raw_content

# 1. 代码块修复
    current_content = fix_code_blocks(current_content)
# 2. 列表符号统一
    current_content = unify_list_symbols(current_content)
# 3. HTML 转义（略，使用 html.escape 处理非代码块区域）

# 4. 验证
    if not verify_markdown(current_content):
# 如果正则修复导致更严重的破坏，回退到原始内容并记录日志
# 这是一个防御性设计，宁可显示格式丑，也不要渲染崩溃
        print("Warning: Sanitization failed verification, falling back to raw.")
        return raw_content

    return current_content```text

### 5. 生产环境考量

上线该管道一周后，我们观察到了显著的变化：

1.**P99 渲染延迟**：从 2.3s 降至 420ms。这听起来违反直觉（加了处理层反而变快？），因为之前前端经常因为格式错误触发了重渲染机制甚至 JS 报错，现在的数据结构非常干净，渲染器可以走极简路径。
2.  **错误率**：格式相关的工单从 8% 降到了 0%。彻底消除了因代码块未闭合导致的页面崩坏。
3.  **Trade-off**：我们需要维护一套正则规则。随着业务发展，可能会出现新的 Markdown 边缘情况，需要定期更新`MarkdownSanitizer`的逻辑。但这比调 Prompt 要容易得多，且结果是可预测的。

### 6. 关键要点

1.  **不要相信 LLM 的格式输出**：在任何需要结构化输出的场景（JSON、Markdown、SQL）下，都必须假设 LLM 会犯错，并构建相应的 Schema Validation 或后处理清洗层。
2.  **软约束 vs 硬约束**：Prompt 擅长处理语义、逻辑和创意（软约束）；代码逻辑擅长处理格式、语法和结构（硬约束）。把结构问题交给代码，把内容问题留给 LLM。
3.  **防御性编程**：在引入自动化清洗工具时，务必加入“验证与回退”机制。自动化脚本一旦出错，影响面通常是批量的，必须要有安全兜底。

工程的艺术在于控制不确定性。通过引入这层薄薄的确定性逻辑，我们驯服了 LLM 的随机性，让整个系统变得更加可靠。```
