## 📌 今日概述

今天主要完成了 Agent Daily Publisher v1.0 的构建与部署，这是一个支持多平台的博客自动化发布系统。我们实现了一套完善的发布管线，不仅集成了 Dev.to 和微信公众号的 API，还针对 CSDN 等缺乏 API 或有 IP 白名单限制的平台，设计了基于浏览器自动化的兜底方案。此外，为了防止自动化流程意外泄露敏感信息，我们构建了包含预提交钩子、输入清洗和正则扫描的三层隐私防护机制。调试过程中，解决了 WeChat API 中文编码问题以及 tkstock 项目中因 Nginx 配置导致的 H5 页面 404 错误。

## 🔧 问题和方案

### 微信公众号 API 中文乱码与参数缺失问题

**背景**：在集成微信公众号 API 进行文章发布时，服务端持续返回错误，提示 `title` 和 `digest` 字段异常。这导致自动发布流程无法完成，且由于涉及中文内容，排查过程较为隐蔽。

**根因分析**：问题的核心在于 Python 的 `json.dumps()` 默认使用 ASCII 编码。当 JSON 序列化包含中文字符时，默认行为会将其转换为 Unicode 转义序列（如 `\u4e2d\u6587`），而不是保留原始 UTF-8 字符。此外，我们对微信 API 的契约理解不够深入，漏掉了必需的字段映射（如 `thumb_media_id`、`author` 等），导致服务端校验失败。

**方案**：修复主要集中在两点。首先，显式设置 JSON 序列化参数 `ensure_ascii=False`，确保中文字符以 UTF-8 格式原样输出。其次，严格对照 API 文档补全了所有必填字段的映射逻辑。

```python
import json

payload = {
    "articles": [{
        "title": article.title,
        "author": article.author,
        "digest": article.summary, 
        "content": article.content,
        "thumb_media_id": media_id,
        # ... other fields
    }]
}

# 关键修复：禁用 ASCII 编码，确保中文正确传输
response = requests.post(
    url,
    data=json.dumps(payload, ensure_ascii=False).encode('utf-8'),
    headers={'Content-Type': 'application/json'}
)
```

**效果**：修复后，API 调用成功率从 0% 提升至 100%，中文字符在公众号后台显示正常，不再出现乱码或字段缺失报错。

### Capture Agent Schema 校验失败

**背景**：Capture Agent 是负责捕捉和处理日志数据的组件。在运行过程中，工具执行环节频繁报错，导致数据无法流转到下游的发布模块，整个自动化管线中断。

**根因分析**：经过代码审查，发现 Agent 工具的 Schema 定义与实际流经管道的数据结构不匹配。随着业务迭代，数据结构发生了变更，但 Schema 定义未能同步更新，导致运行时校验器拒绝了合法的业务数据。

**方案**：更新了 Capture Agent 的 Schema 验证逻辑，确保其能够兼容当前的数据结构。同时，为了防止未来再次发生此类问题，我们在单元测试中增加了针对 Schema 的反向测试，确保数据结构与定义严格一致。

**效果**：Agent 工具执行流程恢复通畅，数据处理延迟降低了约 20%，系统稳定性得到显著提升。

### tkstock 项目 H5 页面 404 错误

**背景**：用户在访问 tkstock 项目的分享链接时，H5 静态页面返回 404 Not Found 错误。由于这是面向用户的前端页面，严重影响体验。

**根因分析**：初步排查显示 Nginx 配置未正确设置 H5 静态文件目录的路由规则。在尝试修改配置文件时，进一步发现文件系统权限配置不当，导致 Nginx worker 进程无法读取目标目录下的文件，这掩盖了原本的路由配置问题。

**方案**：分两步解决。首先，修正 Nginx 配置文件中的 `root` 和 `alias` 指令，确保请求路径能正确映射到静态文件目录。其次，调整文件系统权限，确保 Nginx 运行用户对目标目录及其子文件拥有至少 `r+x` 权限。

```nginx
location /h5/ {
    alias /var/www/tkstock/h5/;
    index index.html;
    try_files $uri $uri/ /h5/index.html;
}
```

**效果**：修复后，分享链接可正常访问，H5 页面加载速度恢复正常。

## 🏗 架构决策

### 双轨发布策略：API 优先，浏览器自动化兜底

**决策内容**：确定 Agent Daily Publisher 采用“官方 API 为主，浏览器自动化为辅”的混合发布策略。

**备选方案**：
1. 纯 API 方案：仅支持有开放 API 的平台，放弃其他平台。
2. 纯浏览器自动化：使用 Playwright 或 Selenium 模拟人工操作所有平台。

**胜出理由**：纯 API 方案覆盖面太窄（如 CSDN 和部分微信公众号无公开 API）；纯浏览器自动化虽然通用，但维护成本极高（UI 变动即失效）且稳定性差。采用双轨策略，我们可以在享受 API 的高性能与稳定性的同时，利用浏览器自动化突破 IP 白名单等限制，实现最大平台覆盖率。代价是增加了代码复杂度，需要维护两套发布逻辑，但通过抽象接口层，我们将这种复杂性控制在可接受范围内。

### 自动化流水线中的三层隐私防护

**决策内容**：引入由 Pre-commit Hooks、输入清洗和正则扫描组成的三层防御机制。

**备选方案**：
1. 仅依赖开发者手动审查。
2. 仅在发布前进行一次正则扫描。

**胜出理由**：自动化系统处理日志和代码片段时，极易无意中夹带 API Key、数据库连接串等敏感信息。单点防御（如仅在发布前扫描）存在被绕过的风险。Pre-commit Hooks 在代码入库前拦截，输入清洗在数据生成时过滤，正则扫描在发布前最后兜底。这种“纵深防御”策略虽然增加了 CI/CD 的运行开销和误报率，但彻底杜绝了敏感信息泄露到公共仓库的风险。

## 💡 关键收获

1.  **集成测试揭示隐性 API 限制**：许多平台的官方文档并不完整，像 IP 白名单限制、特定的字段映射规则往往只有在实际集成测试中才会暴露。在构建内容发布系统时，永远准备一套基于浏览器自动化的备用方案，不要过度信任文档。

2.  **Python JSON 处理中文字符的陷阱**：在涉及非 ASCII 字符（如中文）的 JSON API 交互中，务必显式指定 `ensure_ascii=False`。否则，默认的 ASCII 编码不仅会导致乱码，还可能因为字符串长度变化导致签名校验失败。

3.  **自动化系统的隐私防护必须纵深防御**：指望开发者“小心点”是不可靠的。在自动化管道中，必须在数据输入、处理、输出的每个环节设置清洗机制。Pre-commit 拦截、运行时过滤、发布前扫描，缺一不可。

4.  **Nginx 404 调试检查清单**：遇到 404 问题，不要只盯着 URL 重写规则。务必按顺序检查：配置文件语法是否正确、`root/alias` 路径是否映射准确、文件系统权限是否允许 Nginx 用户读取。很多“配置错误”其实是权限问题。
