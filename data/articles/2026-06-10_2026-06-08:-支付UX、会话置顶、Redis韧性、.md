## 🔧 问题和方案

### 1. 支付按钮的加载状态与成功/失败弹窗

**背景**：用户点击支付按钮后，需要等待后端异步回调。之前只做了简单的禁用按钮，用户无法感知支付是否在进行中，且支付结果（成功/失败）没有清晰的视觉反馈。

**方案**：在按钮上叠加 `CircularProgressIndicator`，同时在支付结果返回后弹出模态对话框，区分成功（绿色勾 + 文字）和失败（红色叉 + 错误原因）。

**效果**：用户反馈明显提升，支付体验从“盲等”变为有明确引导和反馈。

### 2. 会话列表置顶/取消置顶（后端 + 前端 + 数据库）

**背景**：用户希望将重要会话固定在列表顶部，方便快速访问。之前会话排序仅按最后更新时间，无法手动控制。

**根因分析**：缺少存储置顶状态的字段和排序逻辑，用户操作无对应接口。

**方案**：
- **数据库**：在 `conversation` 表增加 `is_pinned` 布尔字段（默认 false）和 `pinned_at` 时间戳，用于排序。
- **后端**：新增 `PUT /conversations/{id}/pin` 和 `PUT /conversations/{id}/unpin` 端点，Repository 层增加 `findByUserIdOrderByPinnedAtDescLastUpdatedAtDesc` 查询。
- **前端**：Flutter 列表项增加 Pin/Unpin 按钮，调用后端 API，成功后本地更新列表顺序并显示 snackbar。

**效果**：用户可自由管理会话优先级，代码结构清晰，后续扩展（如置顶图标、长按操作）方便。

### 3. Redis 缓存韧性失效：连接断开后应用崩溃

**背景**：生产环境 Redis 实例短暂不可用（如网络抖动或重启），导致所有 `@Cacheable` 调用抛出 `RedisConnectionFailureException`，进而引起整个请求失败甚至应用崩溃。

**根因分析**：Spring Cache 默认没有针对 Redis 连接失败的优雅降级，超时时间设置过长（默认 2s），且未配合熔断/回调。

**方案**：
1. 在 `RedisCacheManager` 配置中设置 `setTransactionAware(false)` 并加入自定义 `RedisCacheWriter`，在 `get()` 失败时返回 null 而非抛异常，从而使缓存降级为“miss”，走数据库查询。
2. 添加 `@Cacheable` 的 `unless = "#result == null"` 条件（虽然默认已是这样，但显式声明更安全）。
3. 设置连接超时为 200ms，读取超时为 500ms，配合 `Resilience4j` 的 `CircuitBreaker` 包裹缓存方法，当失败率达到阈值时快速熔断，避免雪崩。

**效果**：Redis 短暂不可用时，应用自动降级为直接查库，恢复后缓存自动重建，不再有崩溃记录。

### 4. 股票实时查询性能：`@Cacheable` 反模式

**背景**：股票价格是实时数据，每次查询结果几乎都不同。`findByQuestion` 端点最初使用了 `@Cacheable(key = "#question.id")`，导致每次请求都先检查 Redis（甚至等待锁），缓存命中率极低（<5%）。

**根因分析**：实时数据不适合缓存，`@Cacheable` 引入的序列化/反序列化、网络开销反而比直接查库更慢。

**方案**：直接去掉 `@Cacheable` 注解，改为调用 Repository 的 `findByQuestionId` 查询数据库（MySQL），并确保该查询走索引。

**效果**：接口平均响应时间从 80ms 降低到 12ms，且消除了 Redis 资源浪费。

### 5. 聊天流式文本导致 UI 卡顿

**背景**：AI 聊天时，后端以 SSE 流式逐字符返回文本，前端采用 Bloc 模式，每个字符到来都 `emit` 新状态，导致整个 widget tree 每帧重建数百次，滑动列表和输入框出现明显卡顿。

**根因分析**：`StreamBuilder` 或 `BlocBuilder` 对每个事件都触发 rebuild，而 Flutter 的屏幕刷新率只有 60fps，逐字符更新远超人眼感知需求，只造成性能浪费。

**方案**：
1. 将文本更新从 Bloc 中剥离，使用 `ValueNotifier<String>` 持有流式文本。
2. 在 `ValueNotifier` 的 `addListener` 中，借助 `Ticker`（来自 `SingleTickerProviderStateMixin`）启动一个“帧同步刷新定时器”，每 16ms 将最新文本赋值给 `TextEditingController`，期间所有字符更新都暂存到缓冲区。
3. 这样，Bloc 状态只在完整消息结束时更新一次（用于标记流结束），而 UI 渲染由 Flutter 自身 vsync 驱动。

**效果**：UI 卡顿完全消除，帧率稳定在 55-60fps，输入框和列表滑动不再受影响。

## 🏗 架构决策

### 决策 1：股票实时查询从 @Cacheable 改为直连数据库

**背景**：见上述第4点。

**考虑过的替代方案**：
- 使用短 TTL（如 1 秒）缓存：但 TTL 太短几乎无意义，且增加复杂度。
- 使用本地缓存（Caffeine）并配合过期策略：引入二级缓存，依然有实时性问题（价格可能差几百毫秒）。

**理由**：实时数据天生不适合缓存。去缓存后，数据库查询在索引支持下足够快（毫秒级），且彻底避免了缓存不一致和额外开销。直接查询更简单、更可靠。

### 决策 2：使用 ValueNotifier + 帧同步定时器替代 Bloc 处理流式文本

**背景**：见上述第5点。

**考虑过的替代方案**：
- 在 Bloc 内使用 `debounce`（防抖）：但防抖会引入固定延迟，影响打字机效果的实时性。
- 继续使用 Bloc，但改为批量更新（如每 50ms 聚合一次）：需要额外定时器管理，且 Bloc 依然持有完整状态，没有减少 rebuild 次数（BlocBuilder 还是对每个新状态 rebuild）。

**理由**：`ValueNotifier` + `Ticker` 模式将 UI 更新与 Flutter 帧同步绑定，是最经济的方式。Bloc 只负责消息生命周期的宏观状态（开始、完成、错误），微观文本渲染交给轻量级 `ValueNotifier`，职责分离更清晰。

## 💡 关键收获

1. **实时数据与缓存的矛盾**：当数据的有效期极短（如股票价格），缓存层反而成为瓶颈。直接走数据库并保证索引优化，往往更优。核心判断标准是“缓存命中率是否显著低于 60%”。低于此值，就要考虑移除缓存或改用本地缓存。

2. **高频 UI 更新应逐帧合并**：任何超过屏幕刷新率的更新（如流式文本、进度条、拖拽位置）都应该用帧同步或 `requestAnimationFrame` 类似的机制合并，避免浪费性能。在 Flutter 中 `ValueNotifier` + `Ticker` 是轻量高效的方案。

3. **缓存基础设施必须有降级策略**：Redis 不是高可用的最后一道防线，应用层必须能优雅处理其故障。Spring Cache 默认不提供降级，需要手动配置 `CacheErrorHandler` 或配合熔断器。

4. **置顶功能是多人协同的试金石**：一个看似简单的交互（置顶/取消置顶），实际上牵涉到数据库 schema 变更（新字段、排序索引）、后端接口设计（分离 pin/unpin 或统一 patch）、前端乐观更新（避免等待响应后刷新）。清晰的层次设计让这些变更可预测、可测试。
