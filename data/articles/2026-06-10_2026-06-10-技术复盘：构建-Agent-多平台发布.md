## 📌 今日概述

今天完成了一个重要的里程碑：构建了完整的 Agent Daily Publisher 系统，实现了从内容生成到多平台分发的自动化闭环。该系统采用 5 阶段 AI 流水线，支持 Dev.to（API）、CSDN（浏览器自动化）和微信公众号（API + 浏览器降级）三种发布模式。同时，针对自动化发布中潜在的安全风险，实施了包含正则过滤、Git 配置隔离和 Pre-commit 钩子的三层隐私防护机制。此外，还解决了 tkstock 项目中 Nginx 路由配置导致的 404 问题。

## 🔧 问题和方案

### 1. 应对 CSDN API 不可用：引入 Playwright 降级策略

**背景**：
在构建多平台发布器时，首选方案通常是调用官方 API，因为其速度快、稳定性高且易于维护。CSDN 官方文档声称提供 Open API，但在实际集成测试中发现该接口无法访问。

**根因分析**：
经过排查，CSDN 的 Open API 服务可能已处于维护状态或已废弃。这揭示了一个在第三方集成中常见的问题：文档与实际服务状态不同步。过度依赖单一 API 通道会导致整个发布流程在服务方变动时瘫痪。

**方案**：
放弃纯 API 方案，转而采用 Playwright 进行浏览器自动化模拟。通过模拟用户登录、填写表单和点击发布按钮，实现了“所见即所得”的发布流程。

```javascript
// 伪代码示例：Playwright 自动化发布流程
const browser = await playwright.chromium.launch();
const page = await browser.newPage();
await page.goto('https://mp.csdn.net/mp_blog/creation/editor');
await page.fill('#title', articleData.title);
await page.fill('.editor-content', articleData.content);
await page.click('#publish-btn');
```

**效果**：
成功绕过了 API 不可用的限制，虽然发布耗时从 API 的毫秒级增加到了秒级，但保证了核心功能的可用性，使 CSDN 渠道重新接入自动化流程。

### 2. 微信公众号 IP 白名单限制与双模发布

**背景**：
微信公众号平台提供了内容管理 API，但出于安全考虑，要求调用方的服务器 IP 必须在后台配置的白名单内。在云原生或动态扩缩容环境中，服务器 IP 往往是动态变化的。

**根因分析**：
云服务器的 IP 不可控性导致了 API 调用失败。每次实例重启或扩容，IP 变更都需要人工去微信公众平台后台更新白名单，这违背了自动化的初衷。此外，API 还需要维护 access_token 的生命周期，增加了系统复杂度。

**方案**：
设计了“API 优先，浏览器降级”的双模发布策略。系统首先尝试调用 API，一旦捕获到 IP 限制或 Token 失效等特定错误码，自动切换到 Playwright 浏览器自动化模式。

```python
# 逻辑伪代码
def publish_to_wechat(article):
    try:
        api_client.publish(article)  # 尝试快速 API 发布
    except IPWhitelistError:
        logger.warning("API受限，切换至浏览器自动化模式")
        playwright_client.publish(article)  # 降级处理
```

**效果**：
消除了对静态 IP 的依赖。即使在 API 因合规问题受限的情况下，系统仍能通过浏览器自动化完成发布，显著提升了系统的鲁棒性。

### 3. 自动化发布中的隐私泄露防护

**背景**：
AI 生成的文章中常包含代码示例，这些代码可能无意中包含数据库连接串、API Key 或内部服务地址。如果直接发布到公网平台，会造成严重的信息泄露事故。

**根因分析**：
单纯依靠运行时过滤是不够的，因为生成的 Markdown 文件可能被直接提交到 Git 仓库。此外，开发人员可能在本地调试时将包含敏感信息的临时文件误推。数据泄露可能发生在三个环节：生成阶段、版本控制阶段和发布阶段。

**方案**：
实施了纵深防御的三层隐私保护机制：

1.  **运行时正则过滤**：在 AI 生成内容后，利用正则表达式扫描并替换敏感模式。
2.  **Git 隔离配置**：在 `.gitignore` 中明确忽略生成的文章目录或包含敏感数据的中间产物，防止误提交。
3.  **Pre-commit Hooks**：在代码提交前强制执行扫描脚本，即便绕过了前两层，也能在最后一道防线拦截敏感信息。

```bash
# .pre-commit-config.yaml 示例
repos:
  - repo: local
    hooks:
      - id: detect-secrets
        name: Detect secrets in generated content
        entry: python scripts/scan_secrets.py
        language: system
        files: (generated_articles/|dist/)
```

**效果**：
构建了自动化发布的安全底线。这种多重检查机制确保了即使 AI 产生幻觉输出敏感代码，也不会流出内网环境。

### 4. Nginx 路由配置排查：404 Not Found

**背景**：
在 tkstock 项目中，本地开发环境正常，但在生产环境中访问 `https://www.tkstock.com/pages/share/dialog?code=xxx` 返回 404 错误。

**根因分析**：
Nginx 的 `location` 块配置未能正确匹配 `/pages/share/dialog` 路径。通常这是因为在配置 `root` 指令时，指定的物理目录路径与 URL 路径结构不匹配。例如，URL 期望找到 `/var/www/html/pages/share/dialog/index.html`，但 Nginx 配置可能将 `root` 指向了 `/var/www/html`，且缺少正确的 `try_files` 规则处理带参数的请求。

**方案**：
审查并修正了 `shop.tkstock.com` 的 Nginx 配置块。确保 `root` 指令指向 H5 应用的构建产物根目录，并添加了 `try_files $uri $uri/ /index.html;` 以支持前端路由（如果是 SPA 应用）。

```nginx
server {
    listen 443 ssl;
    server_name shop.tkstock.com;
    
    location / {
        root /var/www/tkstock-h5; # 确保路径正确指向静态文件根目录
        try_files $uri $uri/ /index.html;
    }
    
    # SSL配置省略...
}
```

**效果**：
修复后，带参数的分享链接能够正确解析并返回 H5 页面，恢复了用户分享功能的可用性。

## 🏗 架构决策

### 1. 5 阶段 AI 流水线设计

**决策内容**：
将 Agent 的处理逻辑拆分为：捕获 -> 分析 -> 撰写 -> 适配 -> 发布 5 个独立阶段。

**为什么这样选择**：
传统的单体脚本将所有逻辑耦合在一起，难以维护。将“适配”独立出来，允许我们针对 CSDN 的 Markdown 语法和 Dev.to 的 Front Matter 做差异化处理，而不需要改动核心的“撰写”逻辑。这种模块化设计使得未来接入新平台（如掘金、知乎）时，只需扩展适配器和发布器，复用上游的分析与生成能力。

**权衡**：
增加了系统的初始复杂度和消息传递的开销，但换来的是极高的可扩展性和并行处理潜力（例如分析与撰写可以并行进行）。

### 2. 双模发布架构

**决策内容**：
不为每个平台死守单一接口，而是为每个平台实现“API + 浏览器自动化”两套驱动，默认优先 API，失败时自动降级。

**为什么这样选择**：
第三方平台的政策变更不可控。CSDN API 的失效和微信 IP 白名单的限制证明了单一依赖的脆弱性。浏览器自动化虽然慢且容易受 UI 变动影响，但它模拟的是真实用户行为，通常是平台最不愿意彻底封禁的路径。

**权衡**：
开发成本几乎翻倍，测试覆盖面也随之变大。需要维护两套逻辑，但在 B2B 内容分发的场景下，稳定性比开发效率更重要。

## 💡 关键收获

1.  **降级思维是第三方集成的核心**：在接入任何外部 API 时，不仅要考虑“正常情况怎么用”，更要设计“API 挂了怎么办”。浏览器自动化、OCR 识别甚至人工介入流程都应作为备选方案纳入架构设计。

2.  **Pre-commit 是防止凭证泄露的最后一道防线**：代码审查可能会漏看，运行时过滤器可能会被绕过，但强制性的 Git 钩子能在代码离开开发者机器之前进行拦截。对于自动化发布系统，这种“左移”的安全措施至关重要。

3.  **动态 IP 环境下的 API 集成策略**：如果目标 API 强制要求 IP 白名单，且基础设施基于云（K8s/Serverless），直接对接 API 会极不稳定。此时应评估使用浏览器自动化或 NAT 网关固定 IP 的成本，往往前者在初期更为灵活。

4.  **Nginx 路径配置的调试直觉**：遇到 404 错误时，首先检查 Nginx 的 `root` 指令路径是否包含了 URL 中的前缀。很多问题源于将 `root` 配置成了上级目录或下级目录，而非文件系统的真实映射点。
