## 🔧 问题和方案

### 1. Claude Code 历史记录读取为空

**背景**
在尝试抓取近期的编码活动数据用于生成日报时，日志读取器返回了空数据。这意味着自动化内容源被切断了，整个流水线失去了输入。

**根因分析**
代码中的日志读取器硬编码了读取全局历史文件路径 `~/.claude/history.jsonl`。然而，Claude Code 实际上是在项目级别的 `.claude/history.jsonl` 文件中存储特定项目的上下文和操作记录。全局文件可能被清空或并未包含我们需要的项目特定上下文。

**方案**
修改日志读取逻辑，使其优先查找并读取项目根目录下的 `.claude/history.jsonl` 文件。这确保了我们抓取的是与当前项目紧密相关的具体开发活动，而非杂乱的全局记录。

```python
# 修改前
history_path = os.path.expanduser("~/.claude/history.jsonl")

# 修改后
project_history_path = os.path.join(os.getcwd(), ".claude", "history.jsonl")
if os.path.exists(project_history_path):
    history_path = project_history_path
else:
    # 回退逻辑...
```

**效果**
成功捕获了 2026-06-09 和 2026-06-10 的完整开发数据，使得每日内容生成管线得以正常运转。

### 2. 微信公众号 API 集成受阻

**背景**
最初计划通过微信公众号官方 API 直接发布文章，以获得最佳性能和稳定性。但在测试环境中，接口调用返回鉴权失败。

**根因分析**
微信公众平台对 API 调用有严格的 IP 白名单限制。这意味着服务器 IP 必须预先在后台配置。对于使用动态 IP（如本地开发、CI/CD 动态构建节点）的环境，这几乎是不可能满足的条件。

**方案**
放弃纯 API 模式，转而采用 **Playwright 浏览器自动化** 方案。同时，为了兼顾效率和风险，我们将策略调整为“API 草稿模式”：利用官方 API 创建草稿，后续通过人工审核后发布。对于完全无法通过 API 访问的场景，则完全依赖浏览器自动化模拟登录与发布操作。

**效果**
绕过了 IP 白名单的基础设施限制，成功实现了微信公众号内容的自动化推送，无需维护固定的服务器 IP。

### 3. AI 生成内容的隐私泄露风险

**背景**
AI 分析代码并生成技术博客时，可能会将代码中的配置项（如 `spring.datasource.password`、Redis 连接串）作为“示例代码”直接写入文章中。如果这些文章被自动发布到公网，后果不堪设想。

**根因分析**
传统的 `.gitignore` 只能防止文件被提交，无法控制 AI 生成文本的内容。AI 在理解代码逻辑时，本质上是在处理数据流，很难区分哪些是“逻辑”哪些是“凭证”。仅仅依靠不提交配置文件是不够的，因为 AI 已经“读”到了这些内容。

**方案**
实施了**三层防御体系**：

1.  **静态文件层**：更新 `.gitignore`，排除所有敏感配置文件（如 `.env`, `config/secrets.yml`）。
2.  **提交钩子层**：配置 pre-commit hooks，在代码提交前扫描是否有敏感关键词（如 `password`, `apikey`）意外混入代码库。
3.  **运行时过滤层（最关键）**：在发布管线中增加一道清洗工序。使用正则表达式扫描 AI 生成的 Markdown 内容，在发布前移除或脱敏所有疑似敏感信息。

```python
import re

def scrub_secrets(content: str) -> str:
    # 定义敏感模式
    patterns = [
        r"password\s*=\s*['\"]?[^'\"\s]+['\"]?",
        r"api[_-]?key\s*=\s*['\"]?[^'\"\s]+['\"]?",
        r"jdbc:[^"]+",
        # 更多模式...
    ]
    for pattern in patterns:
        content = re.sub(pattern, "[REDACTED]", content, flags=re.IGNORECASE)
    return content
```

**效果**
彻底杜绝了数据库凭证、Redis 配置、API 密钥和应用密钥泄露到公开文章或 Git 仓库的风险，建立了可信赖的自动化发布流程。

## 🏗 架构决策

### 1. 多平台发布器架构

**决策内容**
采用统一的发布器接口，内部针对不同平台实现不同的发布策略（API 或浏览器自动化）。

**考虑的方案**
-   **全 API 方案**：理论上最快，但受限于平台权限（CSDN 无公开 API，微信有 IP 限制）。
-   **全浏览器自动化方案**：通用性强，但速度慢，且容易因页面 UI 变动而失效。
-   **混合方案**：根据平台特性选择最优路径。

**选择理由**
混合方案在复杂性和通用性之间取得了最佳平衡。核心流水线无需关心底层是通过 HTTP POST 还是通过 DOM 操作点击按钮，只需调用 `publish(content)`。这让我们能够灵活适配新平台，而不需要重构核心逻辑。

### 2. 项目级历史文件读取策略

**决策内容**
优先读取项目目录下的 `.claude/history.jsonl`，而非全局用户目录下的历史文件。

**选择理由**
全局历史文件往往内容混杂，包含了多个无关项目的操作噪音，且在数据量过大时可能被滚动清理。项目级文件更聚焦，包含的上下文信息（如具体的提示词、文件修改记录）与当前日报生成任务的相关性更高，提取出的技术点更准确。

### 3. 纵深防御的隐私策略

**决策内容**
不依赖单一的安全措施，而是建立文件层、Git 层和运行时层的三层防护。

**选择理由**
在 AI 辅助开发场景下，代码仅仅是输入，输出才是风险所在。即使源代码库是干净的，AI 模型生成的文本也可能包含它从代码中“学到”的秘密。运行时过滤是最后一道防线，也是保障公开内容安全性的必要手段。虽然增加了一些处理开销，但对于发布到公网的内容来说，这是必须付出的安全成本。

### 4. 微信公众号混合发布模式

**决策内容**
使用 API 创建草稿，保留人工审核环节，而非全自动发布。

**选择理由**
完全自动化（直接发布）风险极高，一旦 AI 产生幻觉或过滤规则失效，错误的资讯会直接推送给粉丝。完全手动则失去了自动化的意义。API 草稿模式利用了自动化处理排版和上传图片的优势，同时保留了人工把关的红线，是效率与风控的最佳折中。

## 💡 关键收获

1.  **平台 API 的隐形墙**：永远不要假设所有平台都提供标准化的 API。像 IP 白名单这样的基础设施限制，往往会成为自动化流程的硬伤。在这种情况下，浏览器自动化虽然看起来“笨重”，却是解决实际问题的通用钥匙。

2.  **AI 安全需要运行时干预**：处理 AI 生成内容时，传统的源代码安全工具（如 Git 扫描）是不够的。AI 能够理解并重组数据，因此必须在数据离开系统边界（即发布文章）的那一刻进行运行时清洗。

3.  **数据源的质量决定生成质量**：对于基于日志的自动化内容生成，使用项目级、上下文相关的数据源（如项目特定的 `.claude` 目录）比全局数据源能产生更具针对性的技术总结。

4.  **因地制宜的平台策略**：在 Dev.to 上用 API 只需几毫秒，而在 CSDN 或微信上可能需要模拟浏览器操作耗时数秒。设计系统时要允许不同步调的组件共存，不要为了追求一致性而牺牲可用性。

5.  **Pre-commit 不是银弹**：Pre-commit hooks 能防止开发者手动犯错，但防止不了 AI 将代码中的秘密“复述”进文章里。多层防御必须包含对 AI 输出的处理。
