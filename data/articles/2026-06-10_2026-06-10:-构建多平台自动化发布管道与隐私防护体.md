## 🔧 问题和方案

### 1. Claude Code 历史记录解析失败

**背景**：
Agent 系统依赖读取 Claude Code 的本地历史记录（`history.json`）来生成每日工作日志。但在系统升级到 v2.1.143 版本后，日志捕获模块突然失效，无法读取最近的会话数据。

**根因分析**：
Claude Code v2.1.143 版本更改了日志文件的存储格式，从传统的 JSON 格式迁移到了 JSONL（JSON Lines）格式。原有的 `claude_log_reader.py` 期望的是一个单一的 JSON 对象数组，而新格式每行是一个独立的 JSON 对象，导致解析器抛出异常无法读取数据。

**方案**：
重构了 `claude_log_reader.py`，增加了对文件格式的自动检测逻辑。针对新版格式，代码现在逐行读取文件并分别解析每一行的 JSON 数据：

```python
import json

def parse_history_jsonl(file_path):
    entries = []
    with open(file_path, 'r', encoding='utf-8') as f:
        for line in f:
            if line.strip():
                try:
                    entries.append(json.loads(line))
                except json.JSONDecodeError:
                    continue
    return entries
```

**效果**：
系统现在能够稳定捕获每天 1-2 条历史记录，恢复了数据源的连续性，为后续的内容生成提供了可靠的基础。

### 2. 微信公众号 API IP 白名单限制

**背景**：
在尝试通过官方 API 向微信公众号发布草稿时，请求频繁被拒绝，返回 403 Forbidden 错误。这对于需要自动化发布的系统来说是一个致命的阻断。

**根因分析**：
微信公众号 API 具有严格的安全机制，要求服务器 IP 地址必须在后台配置的白名单中。对于动态公网 IP 环境（如家庭宽带或云服务器自动重置 IP），每次 IP 变更都需要手动去后台更新白名单，这在自动化流程中是不可接受的运维成本。

**方案**：
实施了“双模发布”策略。优先尝试 API 发布（`wechat_api.py`），当检测到网络权限受限时，自动降级到浏览器自动化方案（`wechat_browser.py`）。浏览器自动化通过 Playwright 模拟真实用户登录（扫码认证），绕过了 IP 校验：

```python
# 伪代码示例
class WeChatPublisher:
    def publish(self, content):
        try:
            return self.api_publisher.publish(content)
        except IPWhitelistError:
            logger.info("IP restricted, switching to browser automation")
            return self.browser_publisher.publish(content)
```

**效果**：
成功绕过了 IP 限制，实现了在动态网络环境下的稳定发布。虽然需要首次运行时手动扫码，但相比频繁修改 IP 白名单，极大提升了系统的鲁棒性。

### 3. Dev.to 发布初始化失败

**背景**：
在集成 Dev.to 平台时，API 调用始终返回 401 Unauthorized，导致无法创建文章。

**根因分析**：
经过排查发现两个问题：一是环境变量 `DEVTO_API_KEY` 未正确加载到运行时上下文中；二是 Payload 结构与 Dev.to API 规范不完全匹配（例如缺少必填的 `published` 字段标记）。

**方案**：
将 API Key 配置从临时的 Shell 脚本迁移到了 `.zshrc` 中，确保每次新开终端都能自动加载。同时，修正了 `devto.py` 中的数据封装逻辑：

```python
payload = {
    "article": {
        "title": title,
        "body_markdown": content,
        "published": false, # 先存为草稿
        "tags": ["python", "automation"]
    }
}
```

**效果**：
配置修复后，文章成功通过 API 推送至 Dev.to，并且实现了从环境变量统一管理凭证的目标。

## 🏗 架构决策

### 决策一：针对微信平台优先采用浏览器自动化

- **决策内容**：
在微信公众号的发布策略中，将浏览器自动化作为主要实现方式，而非官方 API。

- **替代方案**：
1. 纯 API 方案：需维护静态 IP 或代理池。
2. 纯浏览器方案：无需 API 配置，但每次需人工介入扫码。

- **选择理由**：
API 的 IP 白名单机制在动态 IP 环境下是极大的运维痛点。虽然浏览器自动化牺牲了部分“无人值守”的能力（需扫码），但它消除了网络层的依赖，使得代码可以在任何能访问互联网的机器上运行，无需复杂的网络配置。权衡之下，可访问性优于完全的无人化。

### 决策二：发布器采用三层抽象模式

- **决策内容**：
设计了 `BasePublisher` 抽象基类，定义 `publish()` 接口。具体实现分为 `ApiPublisher` 和 `BrowserPublisher` 两个子类。

- **替代方案**：
1. 单一函数式实现：每个平台写独立脚本，复用性差。
2. 混杂式实现：在一个类中同时处理 API 和浏览器逻辑，代码臃肿。

- **选择理由**：
这种设计遵循了“策略模式”。它允许我们在运行时灵活切换发布方式（如 API 失败自动切浏览器），同时也便于未来扩展新平台。虽然需要维护多套实现，但代码结构清晰，符合单一职责原则。

### 决策三：构建三层隐私防护体系

- **决策内容**：
在代码提交和文章发布的整个链路中，植入三道安检：(1) Pre-commit Git Hook 扫描敏感词；(2) 运行时 `privacy_filter.py` 检查生成内容；(3) `.gitignore` 物理隔离敏感文件。

- **替代方案**：
仅依赖开发者人工审查，或仅在 Git 层面做检查。

- **选择理由**：
AI 生成内容具有不可预测性，可能会无意中引用训练数据中的密码或配置。仅靠人工审查不可靠，仅靠 Git 检查无法拦截“已生成但未提交”的内容发布到公网。运行时过滤器虽然增加了约 0.1 秒的延迟，但它是防止敏感信息泄露到 CSDN、微信公众号等公网平台的最后一道防线。

## 💡 关键收获

1.  **API 白名单是自动化的隐形杀手**：当第三方 API 强制要求 IP 白名单时，如果基础网络设施不提供静态 IP，不要硬碰硬地去维护代理池，浏览器自动化往往是更具性价比的“降级打击”手段。

2.  **安全必须是多层纵深防御**：对于 AI Agent 系统，单一的安全防线远远不够。Pre-commit 钩子管住了代码库，运行时过滤器管住了输出结果，两者结合才能有效防止 AI“幻觉”导致的数据泄露。

3.  **依赖外部格式需具备版本兼容性**：像 Claude Code 这样的工具，其本地存储格式（如从 JSON 变更为 JSONL）可能随版本更新而改变。解析逻辑必须设计得足够健壮，最好包含版本检测或向后兼容机制，否则工具链极易断裂。

4.  **环境变量是配置管理的最佳实践**：将 API Key、数据库密码等敏感信息注入到 Shell 环境变量（如 `.zshrc`）中，而不是存放在项目的 `config.yaml` 或 `.env` 文件里。这能从根本上杜绝凭证被意外提交到 Git 仓库的风险。
