### 背景与问题：当 Agent 开始“乱说话”

在过去的一周里，我们的 AI 知识库生成系统面临着一个极其恼人的问题：**渲染成功率波动在 85% 到 95% 之间**。对于追求生产级可用性的系统来说，这就是不可靠。

具体表现为：LLM 生成的 Markdown 文档中，代码块经常缺失 `language tag`，出现类似 ` ``` `而没有`python`或`java`的情况；或者更糟，闭合的三反引号` ``` `经常被“吃掉”，导致整个文档页面的样式崩塌，后续段落全部被渲染成代码。这不仅丑陋，更导致下游的文档解析器直接抛出异常。

这是一个典型的 **“概率性垃圾”** 问题。你不能确定 LLM 下一秒是会给出完美的 Markdown，还是给你返回一段格式混乱的文本。当我们试图通过增加 Prompt 中的指令来强制修正时，事情变得更糟——为了强调格式，LLM 开始在正文中加入解释性文字，甚至出现“请将以下渲染为 Markdown”的元指令出现在最终输出里。

### 根因分析：软约束的失效

深入分析后，我们意识到问题的根源不在于 Prompt 写得不够好，而在于我们**试图用软约束去解决确定性的工程问题**。

LLM 的本质是基于概率的下一个 Token 预测模型。当我们在 System Prompt 中写道：“请务必使用标准的 Markdown 格式，代码块必须包含语言标识”时，这本质上只是一个加权建议。在生成上下文中，如果模型对代码内容的置信度高于对格式规则的置信度，或者为了节省 Token，它就会“偷懒”省略格式标签。

此外，我们发现系统主要生成中文技术文档，但所有核心 Agent 的 System Prompt 依然是英文。这种语言不匹配导致了上下文理解的偏差：LLM 需要在脑海中完成“中文指令 -> 英文理解 -> 中文输出”的转换过程，这种认知负荷挤占了用于遵守格式规则的“显存带宽”，导致输出质量的进一步下降。

**根本结论**：依靠 LLM 自觉遵守语法规范，就像依靠前端开发者永远不写 XSS 一样天真。工程上必须引入不可逾越的硬约束。

### 方案深度剖析：构建 Format Sanitizer 管道

为了彻底解决这个问题，我们摒弃了“通过更好的 Prompt 让 LLM 输出正确格式”的幻想，转而构建了 **LLM -> Format Sanitizer -> 持久化** 的确定性流水线。

首先，我们将 6 个核心 Agent 的提示词全面中文化，消除语言转换损耗，让 LLM 专注于内容质量而非语言翻译。但这只是前奏，重头戏在于新增的后处理层。

#### 2. 硬核代码实现：Regex Normalizer

我们实现了一个`FormatSanitizer`类，它不依赖任何 LLM，纯粹基于正则表达式和 AST 解析，确保输出的物理结构正确。

以下是核心的清洗逻辑实现（Python）：
```python
import re
from typing import Tuple

class FormatSanitizer:
    def __init__(self):
# 匹配不带语言标识的代码块开始标记
        self.code_block_start_re = re.compile(r'^([\s]{0,3})```text
(\s*)$', re.MULTILINE)
# 匹配带语言标识的代码块
        self.valid_code_block_re = re.compile(r'^([\s]{0,3})
```(\w+)(.*)$', re.MULTILINE)

    def normalize(self, raw_text: str, default_lang: str = "text") -> str:
        """
        核心清洗逻辑：强制标准化代码块格式
        """
        lines = raw_text.split('\n')
        processed_lines = []
        in_code_block = False
        current_indent = ""

        for line in lines:
# 检测代码块开始
            start_match = self.valid_code_block_re.match(line)
            generic_start_match = self.code_block_start_re.match(line)

            if start_match:
                in_code_block = True
                current_indent = start_match.group(1)
# 这是一个合法的带语言标记的代码块，直接保留
                processed_lines.append(line)
            elif generic_start_match and not in_code_block:
                in_code_block = True
                current_indent = generic_start_match.group(1)
# 关键修复：强制插入默认语言标识，防止渲染器崩溃
# 这里我们将空的```替换为```text 或根据上下文推断
                processed_lines.append(f"{current_indent}```{default_lang}")
            elif line.strip() == "```" and in_code_block:
# 检测代码块结束
                in_code_block = False
                current_indent = ""
                processed_lines.append(line)
            else:
                processed_lines.append(line)

# 兜底逻辑：如果文档结束时代码块未闭合，强制补齐
        if in_code_block:
            processed_lines.append(f"{current_indent}```")

        return '\n'.join(processed_lines)

```text
这段代码的精髓在于它的**防御性**：它不关心代码块里的内容是否合法（那是 LLM 的事），它只关心 Markdown 的“物理边界”是否完整。如果 LLM 忘记写 `
python`，Sanitizer 会默认补上 `text`，虽然可能失去语法高亮，但绝不会破坏页面布局。

#### 3. Save-Verify 循环：最后一道防线

单纯的正则替换有时不够，例如 LLM 可能在代码块内部使用了 Markdown 转义字符。因此，我们引入了 Save-Verify 循环。
```
python
import markdown
from markdown.extensions.extra import ExtraExtension

class DocumentPipeline:
    def save_with_verification(self, doc_id: str, content: str) -> Tuple[bool, str]:
        max_retries = 2
        current_content = content

        for attempt in range(max_retries):
# 尝试解析
            try:
                md = markdown.Markdown(extensions=[ExtraExtension()])
                html_output = md.convert(current_content)

# 这里可以添加更复杂的 HTML 校验，比如检查是否有未闭合的标签
# 但对于 Markdown 转 HTML，库本身已经处理了大部分闭合逻辑
# 我们的校验重点在于：转换过程是否抛出异常，或者是否产生了异常的 AST 结构

# 模拟一个严格的校验：检查代码块是否被正确渲染为 <pre><code>
                if "<pre><code" not in html_output and "
" in current_content:
                     raise ValueError("Code block detected in raw text but not rendered in HTML")

# 校验通过，写入数据库
                self.db.save(doc_id, current_content)
                return True, current_content

            except Exception as e:
                print(f"Attempt {attempt + 1} failed: {e}")
# 如果失败，启动更强力的修复
                sanitizer = FormatSanitizer()
                current_content = sanitizer.normalize(current_content)
# 如果是最后一次尝试且仍然失败，记录错误并降级处理（例如保存纯文本）
                if attempt == max_retries - 1:
                    self.db.save_as_error(doc_id, current_content)
                    return False, current_content

        return False, current_content```### 架构决策记录 (ADR)

| 决策 | 替代方案 | 为什么选这个 |
| :--- | :--- | :--- |
| **硬约束后处理层** | 1. 优化 System Prompt<br>2. 使用 JSON Mode 强制输出 | Prompt 是软约束，无法覆盖所有边界情况；JSON Mode 会限制 LLM 的生成自由度，不适合长文本文档生成。正则清洗提供了性价比最高的确定性保障。 |

| **提示词中文化** | 统一使用英文 Prompt | 目标输出是中文技术文档。语言对齐能减少 Token 消耗，并显著提升专业术语的一致性（例如“递归” vs “Recursion”的混用问题）。 |

### 生产环境考量

在引入这套管道后，我们观测到了以下具体变化：

1.**性能开销**：单次文档生成的 P99 延迟从 1.8s 增加到了 2.1s。这 300ms 的开销主要来自于 Markdown 解析和正则匹配。对于知识库生成这种离线/准实时场景，这个 trade-off 是极度划算的。

2.  **可靠性提升**：文档渲染成功率从波动不定（85-95%）提升至**稳定的 100%**。我们不再需要人工介入修复格式错误的文档。

3.  **维护性**：由于正则逻辑集中在一个模块中，当需要支持新的 Markdown 语法（如 Mermaid 图表）时，我们只需要扩展`FormatSanitizer`，而不需要调整 6 个 Agent 的 Prompt。

### 关键要点

- **永远不要信任 LLM 的输出格式**。在架构设计中，必须把 LLM 视为一个“不可靠的数据源”，并在它之后立即接入清洗层。Prompt 只是为了提升清洗前的质量，减少清洗层的压力，而不是替代清洗层。

- **软约束治标，硬约束治本**。Prompt 工程解决的是“怎么做”的问题（引导 LLM 输出更好的内容），而后处理工程解决的是“必须对”的问题（保障系统接口契约）。

- **语言一致性至关重要**。如果你的服务对象是中文用户，请务必使用中文 Prompt。这不仅能提升用户体验，更能降低 Token 成本并减少模型幻觉。

- **以终为始的校验**。最有效的校验不是检查源码，而是尝试“消费”它。如果你的后处理流程能成功将 Markdown 渲染为 HTML，那么它大概率是正确的。
