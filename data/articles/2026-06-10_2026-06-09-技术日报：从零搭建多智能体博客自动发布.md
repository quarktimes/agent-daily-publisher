## 🔧 问题和方案

### 1. `judge_agent` 中的类型错误：`BaseAgent` 未正确导出

**背景**

我们采用模块化设计，每个 agent 都继承自一个 `BaseAgent` 基类。在 `agents/__init__.py` 中统一导出所有 agent 类，方便外部统一导入。实现 `judge_agent` 时，我们试图 `from agents import BaseAgent`，但运行时抛出 `ImportError`。

**根因分析**

`agents/__init__.py` 最初只导出了具体的 agent 类（如 `CaptureAgent`, `AnalyzeAgent`），但忘记了将 `BaseAgent` 加入导出列表。Python 的 `__init__.py` 导出是显式的，缺失任何导出都会在跨模块使用时立刻暴露。

**方案**

在 `agents/__init__.py` 中添加一行：

```python
from .base_agent import BaseAgent

__all__ = ["BaseAgent", "CaptureAgent", "AnalyzeAgent", "WriteAgent", "JudgeAgent", "AdaptAgent", "PublishAgent"]
```

**效果**

`judge_agent` 成功导入 `BaseAgent`，不再报错。

### 2. Pipeline 中变量命名不一致导致 `AttributeError`

**背景**

Pipeline 编排器按顺序调用各个 agent。我们在 pipeline 定义中用变量 `analyze_result` 存储第一个 agent 的输出，但下游的 writer agent 期望变量名是 `analysis`。运行时直接报 `AttributeError: 'NoneType' object has no attribute 'content'`。

**根因分析**

团队多人并行开发不同 agent，没有提前约定 pipeline 中数据流的关键字命名规范。每个 agent 的输入/输出 schema 虽然定义在各自的类中，但 pipeline 层面的变量绑定是硬编码的，一旦不一致就会出问题。

**方案**

我们统一了 pipeline 中所有中间变量的命名规则：使用 `{agent_name}_result` 模式，并在每个 agent 的文档字符串中明确标注它期望的上游变量名。同时编写了一个 `PipelineValidator` 工具类，在启动时检查所有变量是否连通。

```python
class PipelineValidator:
    @staticmethod
    def check_flow(pipeline_steps: list):
        available = {"session_data": CaptureAgent.capture()}  # 初始输入
        for step in pipeline_steps:
            if step.input_key not in available:
                raise ValueError(f"Missing input '{step.input_key}' for step {step.name}")
            available[step.output_key] = None
```

**效果**

开发者只要遵循命名规范，pipeline 就不会因为变量名不匹配而崩溃。

### 3. Capture Agent 解析历史记录时的数据格式错误

**背景**

Capture agent 需要读取 Claude Code 的会话日志（JSON 格式）并提取关键信息。最初假设日志条目有固定的结构，例如 `{"role": "user", "content": "..."}`，但实际 Claude Log 的数据格式更复杂，包含嵌套的 `parts` 数组和 `metadata`。

**根因分析**

我们在设计时没有先参考真实的数据样本，而是基于文档中的示例结构编写了解析逻辑。真实 API 返回的数据结构往往有差异，尤其是在多轮对话和工具调用场景下。

**方案**

改为使用更健壮的解析策略：先提取所有 `text` 类型的 `parts`，忽略非文本块（如图片 base64）。同时加入了 schema 校验和降级处理：如果某个字段缺失，就跳过而不是抛异常。

```python
def extract_messages(history: list) -> list:
    messages = []
    for entry in history:
        if "content" not in entry:
            continue
        parts = entry.get("parts", [entry["content"]])
        text = "".join(p.get("text", "") for p in parts if p.get("type") == "text")
        if text:
            messages.append({"role": entry.get("role", "user"), "content": text})
    return messages
```

**效果**

Capture agent 现在能正确处理各种 Claude Log 格式，即使字段顺序变化或包含额外嵌套也不会出错。

### 4. DeepSeek API 参数不匹配导致调用失败

**背景**

系统中使用了 DeepSeek 作为模型后端。我们在工具注册表和 publisher 实现中配置了模型名称和 endpoint，但运行时返回 400 错误。

**根因分析**

DeepSeek 的 API 要求使用特定的模型标识符（如 `deepseek-chat`），而我们使用了 `gpt-3.5-turbo` 风格的名字。此外，endpoint URL 缺少版本前缀（`/v1/chat/completions` 写成 `/chat/completions`）。

**方案**

查找 DeepSeek 官方文档，修正配置：

```python
# 修正前
model = "deepseek-v2"
api_base = "https://api.deepseek.com/chat/completions"

# 修正后
model = "deepseek-chat"
api_base = "https://api.deepseek.com/v1/chat/completions"
```

同时将工具注册表中的所有硬编码参数抽取到配置文件中，方便后续切换不同模型。

**效果**

Pipeline 成功调用 DeepSeek API 并返回结果。

### 5. 核心成果：构建完整的“Agent Daily Publisher”系统

**背景**

目标：打造一个能自动记录开发者工作、分析产出、生成技术文章并发布的智能系统。

**实现**

系统由以下六种 agent 组成，形成一个完整的流水线：

| Agent | 职责 |
|-------|------|
| Capture | 捕获 Claude Code 会话日志，提取结构化数据 |
| Analyze | 分析日志，识别主题、亮点、问题等 |
| Write | 基于分析结果撰写技术文章 |
| Judge | 评审文章质量，检查语法、逻辑、长度 |
| Adapt | 适配不同发布平台的格式要求（如 Medium、掘金） |
| Publish | 通过对应平台 API 自动发布 |

此外还构建了：
- **Core 模块**：`BaseAgent`、消息总线、结构化输出定义
- **Tools**：文件读写、API 调用、日志解析等通用工具
- **Workflows**：Pipeline 编排器、MCP 服务器、CLI 脚本
- **Config**：模型参数、平台凭据等集中管理

**效果**

整个系统可以端到端运行：从一句命令开始，到文章自动出现在博客上。这是对多智能体系统设计、AI 编排、API 集成能力的完整实践。

## 🏗 架构决策

### 1. 多智能体架构 vs 单体脚本

**决策**：采用六个独立 agent，每个负责单一职责。

**替代方案**：一个巨大的脚本包含所有逻辑。

**胜出原因**：
- **可维护性**：每个 agent 可以独立测试和部署。
- **可扩展性**：未来要增加“SEO优化” agent，只需新增一个并插入 pipeline。
- **演示价值**：对简历来说是很好的 agent-oriented programming 范例。

**代价**：初期文件数超过 20 个，需要额外处理 agent 间的通信。但通过统一的消息格式和 pipeline 编排器，这个复杂度是可管理的。

### 2. 结构化输出与共享内存模式

**决策**：每个 agent 的输出都定义为 Pydantic 模型，通过共享的 `Context` 对象传递。

**替代方案**：使用纯字典，更灵活但无类型约束。

**胜出原因**：
- **类型安全**：IDE 自动补全和类型检查大幅减少运行时错误。
- **可审计性**：每个 agent 的输出可以被序列化保存，方便调试和复盘。
- **可测试性**：可以 mock 任意 agent 的输出进行集成测试。

```python
class AnalyzeOutput(BaseModel):
    summary: str
    themes: list[str]
    highlights: list[Highlight]  # Highlight 也是 Pydantic model
    architecture_decisions: list[ArchitectureDecision]
```

### 3. 线性 Pipeline vs 有向无环图 (DAG)

**决策**：当前实现为简单顺序执行。

**替代方案**：使用 DAG 编排器（如 Prefect、Airflow）。

**胜出原因**：
- 当前用例是纯顺序的：必须捕获完才能分析，分析完才能写作。没有并行或条件分支。
- 实现简单，没有额外依赖。
- 如果未来需要并行 publish 到多个平台，可以升级为 DAG，但目前不是刚需。

### 4. MCP 服务器 + CLI 双重接口

**决策**：同时提供基于 MCP 协议的交互接口和简单的 CLI 脚本。

**替代方案**：只提供 API 或只提供 CLI。

**胜出原因**：
- **MCP 接口**：允许 Claude Desktop 等工具直接调用 agent，适合交互式调试。
- **CLI 接口**：适合 cron 定时任务或 CI/CD 集成。
- 两者都重用底层 agent 逻辑，代码复用度很高。

## 💡 关键收获

1. **接口定义是第一优先级**：在多智能体系统中，agent 之间的输入/输出 schema 需要提前协商并固化。一个 `__init__.py` 里漏掉的导出，就能让整个 pipeline 停摆。建议在项目初期就使用 `Protocol` 或 `TypedDict` 定义好契约。

2. **文件夹命名一致性是 DevOps 的基石**：虽然只是改大小写，但避免了未来在 Mac（不区分大小写）和 Linux（区分大小写）之间部署时的诡异错误。这种“小事”早做比晚做好。

3. **外部 API 集成要“尽早真实测试”**：DeepSeek 的模型名称、endpoint 版本等细节，只有在真实调用时才会暴露问题。单元测试中 mock 的接口往往过于理想化。建议在开发第一天就写一个最简单的 `curl` 或者 Python 脚本验证连通性。

4. **端到端自主行为是展示技能的最佳方式**：这个项目从“抓取日志”到“发布文章”完全自动化，比写十个孤立 API 演示更能体现架构能力。对于求职面试官来说，一个能跑的、有复杂编排的 demo 胜过千言万语。
